# 検査パイプラインの試運転（2026-09-08）

PR7（検査パイプラインと評価ハーネス）の実装を、実 LM Studio と実原稿で動かした記録。
目的は次の 3 つで、精度の評価ではない（正解データを用いた評価は PR13）。

1. パイプラインが実原稿で完走するかの確認
2. 仕様書 13 節が未決としている値のうち、実測で決められるもの（入力上限の換算係数、タイムアウト）の材料集め
3. モデルと生成設定の当たりをつける

**本書には原稿本文・引用・結果 JSON を載せない。**実原稿はリポジトリ外に置き、コミットしていない。

## 結果 1：統合テスト（合成長文）

3 ファイル / 14 テストすべて通過。`split-recheck` で 4 検査対象・4 指摘・再確認 4 件を 26 秒で完走。
位置特定失敗ゼロ、段落マーカー・区切りタグの引用への混入ゼロ。

**書記素あたりのトークン数（`promptTokens / inputGraphemes`）の平均は 1.146**（8 要求、qwen 思考なし）。

- **脱字（助詞 1 文字の欠落）は両モデルとも見逃した**
- qwen が実原稿に対して 0 件だったことは、この観測の範囲では**誤検出ゼロ**を意味する。
  見逃しの多さと誤検出の少なさのどちらを重く見るかは、正解データがなければ決められない
- 検査対象は 8、全 8 対象が処理され未処理範囲なし

## 結果 3：実装の欠陥の発見と修正（タイムアウトが 300 秒を超えて効かない）

gemma を思考ありで回したところ、実行が `connection-lost`・`generationUnconfirmed: true` で停止した。
原因は LM Studio 側ではなく実装側だった。

- 失敗した要求の所要は **301,289 ms**。呼び出し元が設定したタイムアウトは 900,000 ms
- Node の `fetch`（undici）は `headersTimeout` の既定が 300 秒。`stream: false` では応答ヘッダーが
  生成完了までこないため、**5 分を超える生成は設定値に関わらず切られていた**
- この切断は `AbortSignal` でも自前タイマーでもないため、`timeout` ではなく `connection`（`status` が null）
  に分類され、実行全体の停止を招いていた

修正は `fetch` の `dispatcher` に undici の `Agent({ headersTimeout: 0, bodyTimeout: 0 })` を渡し、
タイムアウトの責任を自前のタイマーに一本化した。詳細と版の制約は `docs/decisions/0003-lm-studio-connection.md`。

**この停止自体は仕様どおりの安全な振る舞いだった。**内訳は次のとおり。

- 停止**前**に完了していた検査 10 単位と、それらから生まれた 13 指摘の再確認 13 件は、そのまま結果に残った
- 停止**後**は、成功済み観点の候補について位置確定・統合・許容語抑制までは実行するが、
  **新しい再確認要求は送らず `pending` にする**
- 残り 5 単位は `pending`（未送信、`attempts: 0`）、通信が切れた 1 単位は `failed`（`attempts: 1`）

誤っていたのは失敗の種別とタイムアウト設定が無効だったことだけである。

## 結果 4：思考ありの挙動とループ

修正後、ループが起きた検査要求の入力（3,317 字）を切り出し、誤字・脱字観点で温度を変えて再現した。

| temperature | 思考あり | 思考なし |
| --- | --- | --- |
| 0 | completed、431 s、思考 7,109 tok、指摘 3 | completed、10.7 s、指摘 3 |
| 0.3 | **`truncated` で 2 回失敗（`partially-failed`）**、初回と再試行の合計 600.4 s | completed、8.8 s、指摘 3 |
| 0.7 | completed、148 s、思考 7,704 tok、指摘 4 | completed、8.2 s、指摘 3 |
| 1.0 | 未実施 | completed、8.2 s、指摘 3 |
| 1.3 | 未実施 | completed、9.0 s、指摘 3 |

この入力に対する qwen（思考なし、同じ 5 条件）はすべて 0 件・0.3 秒（出力 11 トークン）だった。
gemma がこの範囲から一貫して出した 3 件は、**後日の作者の確認により全件が誤検出と判明した**
（実在する慣用表現、古語的な助詞の用法、正当な言い回しを誤りとしたもの）。
この温度実験は `--mode split`（再確認なし）で行ったが、実原稿全体の `split-recheck` の実行では
再確認がこのうちの 1 件を「意図的な表現」として撤回している。仕様 6.5 の再確認が
設計どおり誤検出を落としている例である。

- 最初にループを観測したときの思考は 15,772 トークンで、同じ推論を数百回反復していた（LM Studio のログで確認）
- **今回試した温度の変更では、ループの安定した解消を確認できなかった**。思考ありは 0 で完走し 0.3 で破綻した。
  単一の `seed`・限られた条件の観測なので、「低温がループを誘発する」という一般則の是非も、
  温度で制御できるかどうかも、ここからは決められない
- **思考なしは温度に頑健**。0〜1.3 の 5 条件すべて完走し、指摘数は 3 件で一定。0〜1.0 では指摘内容もほぼ同一で、
  変わったのは分類ラベル（`grammar` と `particle`）と引用範囲の広さだけだった。1.3 で内容が入れ替わった
- `temperature: 0` の 1 要求で比べると、思考あり 431.1 秒に対し思考なし 10.7 秒（約 40 倍）。
  他の温度では条件が揃わないので同じ比較はできない

短文（657 字、1 検査対象、2 観点、思考あり）でも温度 0 / 0.3 / 0.7 / 1.0 を試したが、
4 条件ともループせず、仕込んだ誤りは 4 条件とも検出した。**この短文ではループが再現しなかった**、
という以上のことは言えない（本文が異なるため、入力長が必要条件かどうかは確かめていない）。

## 結果 5：実装の挙動が仕様どおりであることの実機確認

試運転を通じて、モックでしか確認していなかった経路が実機でも動くことを確認した。

- `finish_reason == "length"` を `truncated` として扱い、自動再試行 1 回の後に単位を失敗にする（`attempts: 2`）。
  指摘ゼロに置き換えていない
- 応答を受け取れない通信切断で再試行せず実行を停止し、残りを `pending`、切れた単位を `failed` にする。
  停止した対象でも成功済み観点の指摘は統合・抑制・再確認まで進む
- 431 秒かかる生成が成功する（300 秒の壁の修正の確認）
- 位置特定失敗ゼロ、段落マーカー・区切りタグの引用への混入ゼロ（合成長文・実原稿とも）

## 参考：生成パラメーターの追加可否（実測）

`qwen/qwen3.8-27b`（思考なし、`seed: 1`、同一プロンプト、`max_tokens: 150`）で、パラメーターごとに
対照を取って判定した。まず `temperature: 0` の要求を 2 回送り、出力が完全に一致すること（決定的であること）を
確認したうえで、次の 2 通りの方法で 1 項目ずつ検証した。

- **絞り込み系**：`temperature: 2.0`（基準と異なる出力になることを確認済み）に付与し、
  出力が `temperature: 0` の基準と一致すれば効いている
- **罰則系**：`temperature: 0` に付与し、出力が基準から変化すれば効いている

| パラメーター | 指定値 | 方法 | 出力への影響 | 判定 |
| --- | --- | --- | --- | --- |
| `top_k` | 1 | 高温に付与 | 基準（`temperature: 0`）と一致 | 反映される |
| `top_p` | 0.01 | 高温に付与 | 基準と一致 | 反映される |
| `min_p` | 0.9 | 高温に付与 | 基準と一致 | 反映される |
| `repeat_penalty` | 3.0 | 低温に付与 | 基準と別の文になる | 反映される |
| `presence_penalty` | 2.0 | 低温に付与 | 基準と別の文になる | 反映される |
| `frequency_penalty` | 2.0 | 低温に付与 | 基準と別の文になる | 反映される |
| **`repetition_penalty`** | 3.0 | 低温に付与 | **基準と完全に同一** | **無視されている** |

`repetition_penalty` はエラーにならずに受理されるが出力が変わらない。反映されるのは
`repeat_penalty` の綴りのほうである。**受理されること（HTTP 200）は反映されることを意味しない。**

この検証は 1 モデル・1 プロンプトでの観測であり、他のモデル・ランタイムでの挙動は保証しない。

## 限界

- **正解データがないため、検出率・誤検出率を数値として出していない。**仕込んだ誤り 3 件に対する検出数と、
  再確認の維持・撤回の件数を記録しただけである。実原稿に元からある誤りの総数は不明
- **指摘の正誤を人が検証していない。**本書の初版は指摘件数の多さを検出力と読んでいたが、
  作者の確認により gemma の指摘に誤検出が複数含まれることが分かった。件数を品質の代理指標にしてはならない
- 1 原稿・2 モデル・`seed` 固定 1 値の観測にすぎない。仕様書 10 節が求める複数回実行のばらつきは取っていない
- 許容語を 1 件も渡していないため、抑制の経路は実機で未検証（単体テストでは検証済み）
- 再確認の妥当性（正しい指摘を撤回していないか）は人手で確認していない
- Windows では未実行（CI での `pnpm check` を除く）
- 生成パラメーターの追加可否の検証は 1 モデル（qwen）・1 プロンプト・短い出力での観測である。
  gemma で行った初回の検証は対照を取っておらず、`repetition_penalty` を「反映される」と誤って
  判定していた（ウォームアップによる出力の揺れを効果と読み違えた）。上表は対照付きで取り直したもの

## 今後

- 進め方の当面の方針：**思考なしで校正品質を評価し、思考ありは改善の余地を調べる比較条件として残す**。
  本書の観測からは `temperature: 0` が不適切だとは言えず、思考を有効にする利益も確認できていない。
- モデルと生成設定の確定（仕様書 13 節）は、正解データを用意した PR13 の評価で行う。
  **本書の観測からモデルの優劣は決められない。**指摘の正誤を人が検証しない限り、
  件数の多寡は検出力にも誤検出率にもならないためである。実際、件数の多かった gemma の指摘には
  誤検出が複数含まれていた。確かな比較材料は仕込んだ誤り 3 件に対する検出数（qwen 1、gemma 2）だけである
- 合成原稿と実原稿で挙動が逆転する点に注意が要る。決定記録 0003 の事前調査（合成 906 字）では
  qwen 3/3・gemma 2/3 だったが、実原稿では qwen がほとんど指摘を返さなかった。
  PR13 の評価原稿は実原稿でなければならない
- 入力上限 `maxInputGraphemes` の換算は、実測の 0.98〜1.15 トークン/字を基に決める。
  暫定値 12,000 字は今回の 2 モデル（ロード時コンテキスト長 80,128 と 160,000）に対して安全側だった
- タイムアウトは思考の有無で分ける。1 要求あたりの実測は次のとおり（合計値ではなく 1 要求の値）。
  - 思考なし：実原稿の実行で約 5 秒（gemma、38 要求 193 秒）、切り出し実験で 8.2〜10.7 秒
  - 思考あり：実原稿の実行で 51.8〜149.0 秒（平均 91.8）、切り出し実験で 147.8〜431.1 秒
  暫定値 300 秒は、思考なしには十分だが思考ありでは不足する場合がある（431.1 秒の例がある）
- 思考時のループへの対処として `repeat_penalty` が候補になるが、現在の `ChatRequest` は
  `temperature`・`seed`・`max_tokens`・`reasoning_effort` しか送らない。追加できるかを実測した（下表）。
  これは仕様書 13 節が未決としている「モデルごとの生成パラメーター」の具体化として扱える
