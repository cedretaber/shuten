# 強調表示のスパイク：UTF-16 範囲 → DOM（2026-09-11）

ロードマップ（`docs/plans/2026-09-07-mvp-roadmap.md`）のチェックポイント「強調表示のスパイク」の記録である。
PR12a（結果閲覧）の最難部は「保存済みの UTF-16 範囲を、本文の DOM 上の強調に変換する」ところなので、
設計の前に方式が成立するかを実ブラウザで確かめた。仕様書 5.3 節（本文は空白・改行・段落を保って表示し、
強調箇所から指摘を選べる）・9 節（原文表示と位置情報の対応を保つ）・不変条件
（`docs/reference/invariants.md` の「位置は UTF-16 コード単位」「範囲は書記素境界に揃う」
「ブラウザは表示に使うだけで再計算結果で上書きしない」）を前提にしている。

**結論：方式は成立する。ブラウザ側に書記素境界の計算は要らない。** 保存済み範囲をそのまま
`String.prototype.slice` で切り、段落ごとのセグメント列にして描画すればよい。1 万字・指摘 800 件で
構築 5〜7 ms、DOM 反映 21 ms、選択中の指摘の塗り替え 0.1 ms 未満。仮想スクロールは要らない。
以下は方式の定義と、確かめた事実、PR12a への申し送りである。

検証用のコードはスクラッチ領域にだけ置き、リポジトリには残していない（ロードマップの「コードは残さない」）。

## 方法

- 環境：WSL2（Ubuntu）上から Windows 側の Chrome 152.0.7977.83 を headless（`--headless=new`）で起動し、
  合成本文だけを含む単一 HTML を `--dump-dom` と `--screenshot` で観測した。本アプリの対象環境が
  Windows であるため、Windows 側の Chrome を正とした。C5 の時間だけは同じ条件で 2 回取ってばらつきを見た。
- WSL 側の Chromium（Playwright の chrome-headless-shell 152）でも同じ結果になった。ただし
  C2 の「1 コード単位ずらした分割」を DOM に残したままだと、こちらは `Illegal instruction`（SIGILL）で
  プロセスごと落ちた。その分割を含まないページは同じ環境で正常に動く（C2 を参照）。
- 本文はすべて合成テキストである。実原稿は使っていない。
- 検査項目は C1〜C7 の 7 つ。いずれもページ内で測定し、結果を JSON として取り出した。
  C6・C7 は PR #20 のレビュー指摘を受けて足したものである。

## 検証した方式

段落を単位にブロック要素を作り、その中を「強調が掛かっているか」で区切ったセグメントの列にする。
提案するインタフェース（PR12a で `packages/web` か `packages/shared` に置く。型だけを示す）：

```ts
interface Highlight {
  readonly id: string;          // 指摘 ID
  readonly range: Range;        // 保存済みの UTF-16 範囲 [start, end)
}

interface BodySegment {
  readonly start: number;
  readonly end: number;
  readonly text: string;        // body.slice(start, end)
  readonly findingIds: readonly string[];  // 空なら素のテキスト
}

interface BodyParagraph {
  readonly id: number;          // splitParagraphs の段落 ID
  readonly segments: readonly BodySegment[];
}

function buildBodyView(body: string, highlights: readonly Highlight[]): BodyParagraph[];
```

- 段落分割は `packages/shared/src/text/paragraph.ts` の `splitParagraphs` をそのまま使う。段落範囲は
  末尾の改行列（CRLF・LF・CR）を含むので、表示用にはそれを落とした「内容範囲」を使う。
- 段落ごとに、切れ目の集合＝段落の両端 ∪ その段落に掛かる強調の開始・終了、を作って隣接する 2 点で
  セグメントに切る。各セグメントの `findingIds` は、そのセグメントを完全に覆う強調の ID すべて。
- DOM は `findingIds` が空ならテキストノード、そうでなければ `<span data-findings="id1 id2">`。
  **改行文字は DOM に入れない**（段落ブロックが改行を担う）。容器は `white-space: pre-wrap`。
- 選択中の指摘の塗り分けは、**CSS だけでは書けない**。祖先の属性値（選択中の ID）と子の属性値
  （その位置に掛かる ID）を突き合わせる仕組みが CSS に無いためである。選択 ID を実際に使う方式が要る
  （C6 で 2 通りを実測した）。指摘 ID は UUID（`packages/server/src/db/ids.ts`）で空白を含まないため、
  どちらの方式でも `[data-findings~="<id>"]` で照合できる。**どちらも本文の DOM は作り直さない。**

## 結果

### C1 セグメント化（同一範囲・重なり・入れ子・段落跨ぎ）

4 段落の本文に、同一範囲 2 件・重なり 1 件・入れ子 1 件・段落を跨ぐ 1 件を与えた。

- 同一範囲の 2 件は 1 つの `span` に 2 つの ID として載る（`data-findings="f-same-a f-same-b"`）。
  「同じ範囲の複数指摘をすべて参照可能にする」（仕様書 5.3 節）が、要素を重ねずに満たせる。
- 重なりと入れ子は、覆っている ID の集合が変わる位置で自然に切れた
  （`一行`=2 件 → `目`=3 件 → `の`=1 件 → `テ`=2 件 → `キ`=1 件 → `ス`=0 件）。
- 段落を跨ぐ範囲は段落の境界で切られ、2 つの段落にそれぞれ `span` が出た（`ト。` と `二行目`）。
  間の CRLF は DOM に入らない。
- 各段落のセグメントを連結すると段落の内容と一致し、DOM の `textContent` に改行文字は 1 つも無い。

### C2 Unicode の忠実性（境界に揃った分割 vs 1 コード単位ずらした分割）

5 種類の書記素について、分割なし・書記素境界での分割・わざと 1 コード単位ずらした分割の 3 通りを描画し、
幅と DOM の中身を比べた。

| 例 | コード単位 | 書記素 | 分割なしの幅 | 境界で分割 | ずらして分割 | ずらすと単独サロゲート |
| --- | --- | --- | --- | --- | --- | --- |
| サロゲートペア（U+29E3D） | 6 | 5 | 100 | 100 | 100 | **あり** |
| 異体字セレクタ（葛 + U+E0100） | 7 | 5 | 100 | 100 | 100 | **あり** |
| 結合文字（か + U+3099） | 5 | 4 | 80 | 80 | 80 | なし |
| 絵文字の ZWJ 連結（家族） | 10 | 3 | 65.06 | 65.06 | 65.06 | **あり** |
| VS16 付き記号（❤ + U+FE0F） | 4 | 3 | 67.47 | 67.47 | 67.47 | なし |

- 書記素境界に揃った分割では、字形も幅も分割なしと完全に一致する。**これが主たる確認事項であり、満たされた。**
- ずらした分割でも幅は一致し、スクリーンショットでも字形は崩れなかった。Chrome がインライン要素の境界を
  またいで整形するためである。ただし**強調の塗りが 1 書記素ぶん手前からはみ出す**（本来 `がはねる` から
  塗られるべきところが `𩸽がはねる` から塗られる）。
- さらに、サロゲートペアを割る 3 例では DOM に単独サロゲートが残る。このとき観測した事実は次の 2 つ。
  Windows の Chrome では `--dump-dom` が何も出力しなかった。WSL 側の Chromium 152 では
  `Illegal instruction` でプロセスが落ちた。**測定後に単独サロゲートを含まない表記へ置き換えるだけで、
  どちらも同じページを正常に出力した**（他の条件は変えていない）。原因の断定はしないが、
  単独サロゲートの有無が唯一の差であり、**ずらした分割は描画に現れないまま後段の処理を壊しうる**と見てよい。
- したがって PR12a のテストは描画結果ではなく、`buildBodyView` が返すセグメント列
  （`start` / `end` / `findingIds`）を対象にすべきである。

### C3 空白と改行の保持

`　全角字下げの段落。CRLF CRLF 空行のあと。LF LF LF 三連の空行。CR 末尾は CR 単独。` を描画した。

- 段落は 7 つに分かれ、CRLF・LF・CR のいずれも 1 つの区切りとして扱われた。
- 空行は空の段落ブロックとして残り、`min-height` により高さ 30 px（行の高さ）を保った。つぶれない。
- 行頭の全角スペースは保持された（`white-space: pre-wrap`）。
- DOM の `textContent` に CR は含まれない。

### C4 移動と選択

60 段落の本文に 4 件の強調（うち 2 件は重なり）を置いた。

- 51 段落目の強調へ `scrollIntoView({ block: "center" })` でスクロールできた（`scrollTop` 1434）。
- 重なっている位置の `span` は `data-findings` に 2 つの ID を持ち、クリックから両方の指摘を辿れる。
- 選択中の指摘を切り替えても **DOM の再構築は 0 回**だった。ただしこのケースで測ったのは容器の属性の
  差し替えと該当 `span` の照合だけで、**実際に塗り分けられることは確かめていない**。塗り分けの方式と
  その時間は C6 で測り直した。

### C5 規模

1 文あたり約 34 字の合成本文に、等間隔で 4 コード単位の強調を置いた。各 2 回測定。

| 本文 | 段落 | 強調 | span | 構築 | DOM 反映 | 容器の属性の差し替え |
| --- | --- | --- | --- | --- | --- | --- |
| 1 万字 | 278 | 800 | 800 | 7.3 / 4.5 ms | 20.5 / 22.1 ms | 0.7 / 0.7 ms |
| 10 万字 | 2,778 | 2,000 | 2,111 | 30.4 / 22.9 ms | 63.2 / 59.8 ms | 2.6 / 2.7 ms |

仕様書 9 節の主な評価対象は 1 万字程度なので、**仮想スクロールも遅延描画も要らない**。
その 10 倍でも 0.1 秒未満に収まる。
（10 万字で span が強調の数より多いのは、段落を跨ぐ強調が段落境界で切られるためである。
最後の列は容器の属性を差し替えただけの時間で、選択中の指摘の塗り分けそのものは C6 で測った。）

### C6 選択中の指摘の塗り分け

CSS には属性値どうしを突き合わせる仕組みが無いので、「容器に選択 ID を置き、CSS で
`data-findings` と照合する」ことはできない。実装しうる 2 方式を、C5 と同じ本文で実測した
（背景色を `getComputedStyle` で確かめ、選択を別の指摘へ移したときに前の強調が基の色へ戻ることも見た）。

| 方式 | 1 万字・800 件（初回 / 切り替え） | 10 万字・2,000 件（初回 / 切り替え） |
| --- | --- | --- |
| A：選択のたびに CSS 規則 1 本を差し替える | 19.8 ms / 0.2 ms | 54.7 ms / 0.8 ms |
| B：該当する `span` に class を付け外しする | 0.1 ms / 0.0 ms | 0.6 ms / 0.1 ms |

- どちらも塗り分けは正しく効き、**本文の DOM の再構築は 0 回**。
- 方式 A の初回が重いのは、規則の追加で文書全体のスタイル再計算が走るためと見られる（2 回目以降は速い）。
- 方式 B は該当する `span` だけを触るので一貫して速く、React でも書きやすい。**方式 B を推す。**

### C7 本文末尾の改行

本文が改行で終わる場合を 6 通り描画した（`splitParagraphs` は末尾の改行の後ろに段落を作らない）。

| 本文の末尾 | 段落数 | ブロック数 | 表示される行 |
| --- | --- | --- | --- |
| 改行なし（`…二行目。`） | 2 | 2 | 一行目。/ 二行目。 |
| LF（`…二行目。\n`） | 2 | 2 | 一行目。/ 二行目。 |
| CRLF（`…二行目。\r\n`） | 2 | 2 | 一行目。/ 二行目。 |
| CR（`…二行目。\r`） | 2 | 2 | 一行目。/ 二行目。 |
| 改行 3 つ（`…二行目。\n\n\n`） | 4 | 4 | 一行目。/ 二行目。/ 空行 / 空行 |
| 空行を挟んで CRLF（`一行目。\r\n\r\n三行目。\r\n`） | 3 | 3 | 一行目。/ 空行 / 三行目。 |

- **末尾の改行 1 つぶんは表示に現れない。** 末尾が LF・CRLF・CR のいずれでも、改行が無い場合と
  同じ 2 ブロック・同じ高さ（61 px）になる。改行が n 個並べば空行は n−1 個になる。
- これは表示の都合ではなく `splitParagraphs` の段落の定義（区切りの改行は直前の段落に含め、
  末尾の改行の後ろには段落を作らない）から来るもので、サーバー側の位置計算と同じ定義である。
  途中の空行は正しく残る（最後の 2 行）。
- 読み取り専用の表示なので実害は小さいが、原稿の行数と表示の行数がずれる。PR12a で扱いを決める
  （申し送り 8）。

## PR12a への申し送り

1. **ブラウザ側で書記素境界を計算しない。** 保存済み範囲をそのまま使う。`Intl.Segmenter` も
   `packages/shared/src/text/grapheme-index.ts` も、結果閲覧の画面では使わない。
2. **テストはセグメント列に対して書く。** C2 のとおり、分割位置のずれは描画では見つからない。
   絵文字・異体字セレクタ・結合文字・CRLF を含む本文で、`buildBodyView` の出力の `start` / `end` /
   `findingIds` を検査する。加えて「どのセグメントにも単独サロゲートが無い」ことを検査すると、
   ずれをそのまま捕まえられる。
3. **jsdom でできないことがある。** `packages/web` のテストは jsdom で動く。実測したところ、
   `[data-findings~="id"]` の照合は動くが、`getBoundingClientRect()` は常に 0 を返し、
   `scrollIntoView` は**存在しない**（`TypeError`）。移動の検査はスタブを置いて「呼ばれたこと」までにし、
   幾何や実際のスクロール位置は検査しない。
4. **段落ブロックに改行文字を入れない。** 段落範囲は末尾の改行列を含むので、表示では落とす。
   空段落は `min-height` でつぶれないようにする。
5. **選択状態を本文のセグメントに持たせない。** 本文のセグメント列は選択と無関係に作り、選択の塗り分けは
   該当する `span` への class の付け外し（C6 の方式 B）で行う。CSS だけで選択 ID と `data-findings` を
   照合することはできない。React では、本文は選択状態に依存しないコンポーネントにし、塗り分けは
   `ref` から該当要素を引いて class を操作する（再レンダリングを起こさない）。
6. `buildBodyView` は段落ごとに全強調を走査する素朴な実装（O(段落数 × 強調数)）でも 10 万字で 23〜30 ms
   だった。指摘が桁違いに増えたときだけ、開始位置で整列して走査する形に変えればよい。
7. 位置特定失敗（`not-found` / `ambiguous`）や `outside-target` の指摘は `range` を持たないか強調しないので、
   `highlights` に渡さない。渡す集合を決めるのは呼び出し側（絞り込み）の責務にする。
8. **本文末尾の改行の扱いを決める。** C7 のとおり、素直に作ると末尾の改行 1 つぶんが表示に現れない。
   原稿の行数と表示の行数を合わせるなら、本文が改行で終わるときに空のブロックを 1 つ足す。
   足さないと決めるなら、その旨を計画書に書いて検査（末尾が LF・CRLF・CR の 3 通りと連続する末尾改行）を
   置く。どちらでも位置の対応は変わらない（強調範囲が末尾の改行に掛かっても、塗る範囲が縮むだけである）。

## 確かめていないこと

- **React での再測定。** 計測は素の DOM 操作で行った。セグメント列を作る部分の時間は変わらないが、
  DOM 反映の時間には React 自身の処理が乗る。PR12a で実装したあとに 1 万字で測り直す。
- **Chrome 以外のブラウザ。** 対象環境が Windows + Chrome 系なので確認していない。C2 の「ずれても字形が
  崩れない」は Chrome の整形の挙動に依るため、他のブラウザでは崩れる可能性がある（申し送り 2 の結論は変わらない）。
- **実原稿での確認。** 合成本文のみ。実原稿での確認は PR13b の評価に含める。
