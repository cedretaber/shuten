# 0003. LM Studio 接続検証の結果

日付：2026-09-07  
状態：決定（初回検証。数値は同一環境での 1 回計測であり、評価時に再計測する）

## 検証環境

| 項目 | 値 |
| --- | --- |
| LM Studio | 0.4.23+1（Windows） |
| 推論ランタイム | llama.cpp-win-x86_64-nvidia-cuda12-avx2 2.33.0 |
| モデル | `qwen/qwen3.8-27b`（Q4_K_M、17.74 GB） |
| ロード時コンテキスト長 | 201,728 トークン |
| LM Studio 側の並列数 | 4（`lms ps` の PARALLEL 列。アプリは単一キューで使う） |
| 接続元 | WSL2（Ubuntu）。アプリは将来 Windows 上で動かす |
| 生成速度 | 約 100〜105 トークン/秒（思考を含む出力側） |

## 接続先

- Windows 上で動かす場合は `http://127.0.0.1:1234/v1`（仕様書 7 節の初期値のまま）。
- WSL2 から Windows 側の LM Studio へは `localhost` / `127.0.0.1` では届かない。
  Windows ホストの IP はデフォルトゲートウェイと一致する。今回は `172.28.80.1`。
  この IP は WSL の再起動で変わり得るため、設定に固定値を書かず、必要なら次で導出する。

  ```sh
  ip route | awk '/default/ {print $3}'
  ```

- LM Studio 側は「ローカルネットワークで公開」に相当する設定が必要（WSL からの到達で確認済み）。
- Windows 側の `lms` CLI（`/mnt/c/Users/<user>/.lmstudio/bin/lms.exe`）は WSL から直接実行でき、
  `lms ps` でモデルの状態（IDLE / GENERATING）を観察できる。開発時の診断に使う。
- アプリからモデルの状態を取るには LM Studio 固有の `GET /api/v0/models` を使う。
  `state`（loaded / not-loaded）、`quantization`、`loaded_context_length` が取れ、
  仕様書 10 節で実行ごとに記録する項目に対応する。OpenAI 互換の `/v1/models` には状態が含まれない。

## JIT ロードによる VRAM 溢れ（検証中に発生した失敗）

モデルが未ロードの状態で、モデル名を指定した生成要求を送ったところ、LM Studio が JIT ロードを開始し、
LM Studio 側のモデル既定値であるコンテキスト長（約 26 万トークン）でロードしようとして VRAM が溢れた。
約 104 秒後に `{"error": "Model unloaded by user or API request."}` が返り、ユーザーが手動で
コンテキスト長を約 20 万に下げてロードし直した。

- この環境では JIT ロードが有効。未ロードのモデルへの生成要求は、アプリの意図とは無関係に
  LM Studio の既定値でロードを引き起こす。
- 仕様書 7 節は接続確認で小さな生成をウォームアップに使うとしているが、この環境ではその小さな生成が
  VRAM 溢れを引き起こし得る。**接続確認では先に `/api/v0/models` で `state` を確認し、`not-loaded` なら
  生成要求を送らずに「LM Studio 側でモデルをロードしてください」と案内する。** ロードは LM Studio 側に
  委ねる（仕様書 7 節「独自のモデル管理機能は持たない」と整合）。
- モデル名を指定しない要求は、未ロード時に即座に 400（No models loaded）で返る。ロードは起きない。

## HTTP 切断で生成が止まるか（仕様書 8.2 節・13 節）

**止まる。** 3 通りで確認した。

| 方法 | 切断後の状態 |
| --- | --- |
| curl、`stream: true`、6 秒後に kill | 1 秒以内に GENERATING → IDLE、GPU 使用率 87% → 3% |
| curl、`stream: false`、6 秒後に kill | 同上（応答を書き出す前でも切断を検知する） |
| Node 24 の `fetch` + `AbortController.abort()`、3 秒後 | 同上。`fetch` は `AbortError` で reject |

したがって、仕様書 8.2 節の「HTTP 接続の切断をキャンセル要求として扱う」は本環境で成立する。
ただし仕様の原則どおり、切断は「通信の中断」であり、生成終了の確認手段は別に持つ
（`lms ps` の状態、または後続の小さな要求の成功）。切断で止まらない環境への備えとして
「復旧待ち」の経路は残す。

## 応答形式

- 思考モデルの出力は `message.reasoning_content` に分離され、`message.content` には本文だけが入る。
  ストリーミングでも `delta.reasoning_content` として分離される。
  `content` 内に `<think>` は現れなかったため、仕様書 7 節の「JSON 外側の思考部分を分離して再解析」は
  この組み合わせでは不要。他モデルで必要になった場合に限定して実装する。
- `usage.completion_tokens_details.reasoning_tokens` で思考トークン数が取れる。実行記録に保存する。
- `response_format: { type: "json_schema", strict: true }` に対応。スキーマどおりの JSON だけが返る。
- `finish_reason: "length"` のとき `content` は空文字になる（思考が予算を使い切った場合）。
  仕様どおり成功扱いしない。
- `seed` に対応。temperature 0.7 でも同じ seed で完全に同じ出力、別 seed で別の出力になった。
  比較実験では seed を固定する。

## 思考（reasoning）の扱い

本節の数値と挙動は `qwen/qwen3.8-27b` に固有のもの。モデルを変えると `reasoning_content` の有無、思考量、所要時間が変わるため再計測する。

- **思考は止められない。** `chat_template_kwargs: { enable_thinking: false }`、`reasoning: { effort: "none" }`
  は無視され、`/no_think` は出力を変えるだけで思考は続いた。常時思考するモデルとして扱う。
- 思考は英語で行われ、本文の各文を順に検討する。906 字の検査対象で約 8,400 トークン、86 秒。
- `max_tokens` は思考を含めて予算配分する。初回検査（1,500 字目標）の初期値は **16,000** とし、
  実測で調整する。8,000 では実文でも不足し得る。
- 反復の多い合成テキスト（同じ段落の繰り返し）では、思考が「反復は誤りか」を延々と検討して
  40,000 トークンでも終わらなかった。実文では起きていないが、思考の暴走は起こり得るものとして
  `max_tokens` 到達を「出力打ち切り」として記録し、再試行 1 回の後は失敗として残す（仕様書 7 節）。

## 品質の初期観察（1 回のみ、評価ではない）

906 字の創作文に重複（かけけた）、助詞抜け（こと考えず）、誤変換（下え）を 1 件ずつ埋め込んだところ、
3 件すべてを検出し、誤検出はなかった。引用は 3 件とも原文に 1 回だけ完全一致し、位置を確定できた。
`after` の 1 件は改行を省いていたが、引用だけで一意なので仕様書 6.2 節のとおり失敗にしない。

一方、最初の小さな試行（「駅にに向かった」）では空配列が返り、思考の中で「助詞の重複は誤字ではなく
文法の問題」と判断していた。誤字・脱字と不自然さの観点をどう定義してプロンプトに書くかが
検出率に直結する。プロンプト設計は評価原稿で詰める。

## 所要時間の見積もり

906 字で 86 秒（思考 8,400 トークン）。思考量は本文長にほぼ比例すると仮定すると、
1,500 字の検査対象で 1 観点あたり 2〜2.5 分、1 万字の原稿（7 分割 × 2 観点）で初回検査に約 30 分、
再確認を加えてさらに増える。仕様書 9 節の「上限と所要時間は実測後に決める」はこの値を出発点にする。
