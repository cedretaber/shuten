# 朱点（shuten）MVP仕様書

- 作成日：2026-09-06
- 改訂：2026-09-11 結果画面の本文表示の例外を追記（v0.9.1）
- 状態：実装前の仕様案（確定）
- 対象：Windows上のローカル環境、単一ユーザー

## 1. 目的

日本語の小説から誤字・脱字と日本語として不自然な箇所を検出し、作者が原文と照合して効率よく判断できる校正ツールを作る。

細部まで読み直す負担を減らし、誤りの見逃しを減らすことを最優先とする。指摘数を増やすこと自体を目的にしない。作者の文体や表現意図を尊重し、本文の書き換えは作者の判断に委ねる。

MVPでは、LM Studioとの接続、分割検査と再確認の有効性、指摘の品質、確認作業の負担を実際の原稿で評価する。

## 2. 前提と決定事項

- LLMは既存のLM Studio環境で動作するローカルモデルを利用する。
- ユーザーの実測では中規模モデルで必要な速度と校閲能力が得られている。ただし本アプリによる性能は未検証である。
- ブラウザで操作するWeb UIと、同一PC内のバックエンドで構成する。
- MVPの標準実行環境はWindowsとし、バックエンドもWindows上で動かす。開発ツールをWSLで使うことと、アプリをWSLで実行することは区別する。WSL上で実行する場合は、LM Studioへの接続設定（ネットワークモード、接続先アドレス）を環境に合わせて確認する。
- 初期版は単一モデルを利用する。バックエンド全体で単一の実行キューを持ち、複数タブ・複数原稿・接続確認を含むLLM生成要求の同時実行数を1に固定する。UIの設定項目にはしない。
- 本文を一定長に分割し、誤字・脱字と日本語の自然さを別々に検査する。
- 指摘候補は前後の文脈を広げて再確認する。
- 指摘一覧だけでなく、本文の該当箇所への移動と強調表示を提供する。
- MVPの採否操作は評価の記録であり、本文への修正適用ではない。

「合意した機能範囲」と「実装時に調整する初期案」を区別する。本書の初期値は確定した最適値ではない。

## 3. 対象と対象外

### 3.1 対象とする検査

| 分類 | 対象例 | 出力方針 |
| --- | --- | --- |
| 誤字・脱字 | 誤変換、文字の欠落・重複、助詞の抜け、括弧の閉じ忘れ | 根拠と最小限の修正案を示す |
| 不自然な日本語 | 主述の不一致、係り受け、助詞の使い方、語の組み合わせ、修飾関係の不明瞭さ | 不自然と判断する理由を具体的に示す |

体言止め、倒置、省略、口語、方言、意図的な反復、造語は、それだけを理由に誤り扱いしない。意味が成立する文から作者の意図した脱字を確定できない場合は、確認事項として提示する。

### 3.2 MVPの対象外

- 設定、時系列、人物の知識、口調、ストーリー、動機の整合性検査。
- 文章を美しくする提案、冗長さの削減などを目的とした推敲。
- 日本語辞書RAG、作品資料RAG、複数モデルの相互相談。
- 本文への修正適用、本文上の手動編集、変更履歴、取り消し・やり直し、修正済み本文の出力。
- 学習やファインチューニング、採否からの自動的な校正方針変更。
- クラウド公開、複数ユーザー、スマートフォン向けの専用対応。
- Word・PDFの読み込み、ルビなどの特殊な原稿記法の専用解析。
- 近似一致による指摘位置の自動割り当て。比較による候補取得は診断専用とする。

## 4. 基本操作

1. ローカルの校正アプリを起動し、ブラウザで開く。
2. LM Studioの接続先を設定し、接続確認とモデル選択を行う。
3. 原稿を貼り付ける、またはUTF-8のテキストファイルを読み込む。
4. 検査観点、分割長、再確認の有無などを確認して検査を開始する。
5. 完了した範囲から結果を確認する。指摘を選ぶと本文の該当箇所へ移動する。
6. 原文、理由、修正案を確認し、「採用予定」「却下」「保留」を記録する。
7. アプリを再度開いたときに保存された結果と採否を読み込める。

検査開始時点の本文を変更不能なスナップショットとして保存する。別の本文を入力して検査する場合は、新しい原稿版を作成する。

## 5. 画面仕様

### 5.1 接続・入力

- 接続先URL、モデル選択、接続確認ボタン。
- APIキー設定欄は認証が必要な環境に備えて用意する。通常の結果出力やログには含めない。
- 原稿名、本文貼り付け欄、テキストファイル読み込み。
- UTF-8（BOMありを含む）を受け付ける。読み込み不能な場合は文字コードの問題を表示し、黙って置換しない。ファイル先頭のBOMだけを本文から除外し、それ以外の文字・空白・改行は無加工で保存する。
- 貼り付け入力はブラウザから受け取った文字列を基準とし、貼り付け元での改行形式の復元は保証しない。ファイル入力はCRLFを含む元の改行を保持し、編集欄の改行変換を保存本文へ逆流させない。
- 空の本文では検査を開始できない。

### 5.2 検査設定

| 設定 | 初期案 |
| --- | --- |
| 検査観点 | 誤字・脱字、日本語の自然さの両方 |
| 検査対象の分割長 | 目標1,500字。調整可能 |
| 初回の参考文脈 | 検査対象の前後各1,000字を目標とし、段落境界を優先して丸める |
| 再確認 | 有効。比較実験のため無効化可能 |
| 再確認の参考文脈 | 元の検査対象の前後各3,000字を目標とし、段落境界を優先して丸める |
| 許容語 | 固有名詞、造語などを改行区切りで登録可能 |

分割長と文脈長の「字」は書記素クラスタ数を基準とし、位置保存に使うUTF-16コード単位やモデルのトークン数とは区別する。前後の文脈長は検査対象の外側から数える。短い会話段落でも目標文字数まで複数段落を含める。

段落境界への丸めは、初期案として目標の±20%内で最も近い境界を選び、同距離なら外側を選ぶ。適切な境界がなければ目標位置の書記素クラスタ境界で切る。本文端では存在する文脈だけを使用する。再確認の入力には初回の入力範囲を必ず含め、利用可能な周辺本文があれば広げる。入力上限を超えた場合は黙って縮めず、エラーとして設定変更を案内する。

許容語はプロンプトのヒントと、6.4の限定的な後処理に併用する。語の登録だけで周囲の文法や文脈上の誤用まで免除しない。

生成パラメーターはモデルとの相性を接続検証で確認し、実行ごとに記録する。温度などの最適値や推論モードは現時点で固定しない。

### 5.3 結果画面

- 上部：原稿名、検査状態、観点別の処理進捗、停止・再開操作。
- 左側：読み取り専用の本文。空白、改行、段落を保った表示。ただし本文末尾の改行1つは表示上の空行にしない（6.1節の段落の定義上、末尾の区切りの後に段落が無いため）。保存する本文と位置情報は変わらない。
- 右側：指摘一覧と選択した指摘の詳細。
- 位置が特定できた指摘のクリックで該当箇所へ移動し、対象範囲を強調表示する。
- 位置特定失敗の候補も一覧に表示し、LLMの引用と理由を確認できるようにする。強調表示は行わず、元の検査対象範囲への移動だけを提供する。診断用の類似候補は通常の指摘位置と区別して詳細表示する。
- 本文の強調箇所から対応する指摘を選択できる。同じ範囲に複数指摘がある場合はすべて参照可能にする。
- 分類、採否、再確認状態、位置特定失敗による絞り込みを提供する。許容語による抑制候補と再確認で撤回された候補は通常非表示とし、切り替えて閲覧できる。
- 「未判断」「採用予定」「却下」「保留」を区別し、判断は変更できる。
- 「採用予定」は本文を書き換えないことを操作付近に明示する。

### 5.4 指摘詳細

- 分類と短い見出し。
- 位置確定時は原文の正確な引用。位置特定失敗時は「LLMの引用（原文との一致未確認）」として表示。
- 最小限の修正案。修正を特定できない場合は未提示を許可する。
- 指摘理由と、必要なら判断に迷う点。
- 「誤りの可能性が高い」「作者への確認事項」の区別。
- 再確認済み、再確認なし、再確認待ち、再確認失敗などの状態。
- 採否と任意の判断メモ。

初回検査は暫定判定を付与する。再確認が正常終了した場合のみ、その結果を表示上の最終判定とする。初回判定は履歴に保持し、再確認待ち・失敗・無効の場合は未検証の初回判定とその状態を示す。再確認は作者の採否を上書きしない。

原文と修正案は並べて比較できればよい。変更文字単位のdiffはMVPの必須機能としない。モデルの自己申告による確信度を確率として表示しない。

## 6. 検査処理

処理順序は「分割 → 観点別検査 → 引用・位置検証 → 重複統合・許容語後処理 → 再確認 → 結果表示」とする。位置特定失敗は独立した表示経路で扱う。

### 6.1 分割と検査範囲の保証

本仕様の段落は、CRLF・単独LF・単独CRのいずれか1つの改行列で区切られた行と定義する。CRLFは1つの区切りとして扱い、空行も保持する。字下げの全角スペースや画面上の折り返しは段落境界としない。段落IDは原稿版内で出現順に固定する。

位置の基準はBOM除外後の保存本文とし、CRLFのCRとLFはそれぞれ1 UTF-16コード単位として数える。範囲は開始を含み終了を含まない `[start, end)` とする。区切りの改行列は直前の段落範囲に含め、本文全体を隙間なく扱う。

1. 原稿のスナップショット、原稿版ID、段落ID、文字位置を作成する。
2. 段落境界を優先し、目標文字数前後で検査対象範囲を区切る。
3. 単一段落が長い場合は文境界を優先して分割し、それでも長い場合は書記素クラスタ境界で分割する。サロゲートペア、異体字セレクタ、結合文字、絵文字の連結、CRLFの途中では切らない。
4. 全本文の各位置が検査対象のいずれかに属するよう管理する。参考文脈は重複してよい。
5. 境界をまたぐ表現を扱えるよう前後の文脈を添え、指摘の開始位置を含む検査対象範囲がその指摘を担当する。

モデルには「検査対象」と「参考文脈」を明示する。参考文脈だけにある指摘は、その担当範囲で扱う。全範囲の処理完了は見逃しゼロを意味しない。

### 6.2 観点別検査

- 各範囲に対して、選択した観点を別々の要求として送信する。
- 要求間で会話履歴や他の検査結果を共有しない。
- 本文は検査対象のデータとして区切り、本文中の命令文に従わない指示を与える。これによってプロンプトインジェクションを軽減するが、LLMの完全な非追従は保証しない。出力の形式・引用検証も併用し、代表的な命令文を含む原稿で逸脱の有無を評価する。
- 該当なしの場合は空の指摘配列を返させる。件数のノルマは設けない。
- 指摘は段落ID、正確な引用、前後の引用、理由、修正案などを含む構造化データで受け取る。前後の引用は必須キーとし、本文端では空文字を許可する。引用だけで位置が一意に決まる場合は、前後の引用の不備だけを理由に位置特定失敗にしない。

### 6.3 引用と位置の検証

- 文字位置はアプリが原文から確定する。LLMが返した数値だけを信用しない。
- 引用が完全一致で実在するか、参考文脈を含む要求の入力全体を対象に照合する。MVPでは近似一致による位置の確定を行わない。
- 引用の開始位置が検査対象内にある候補だけを採用候補とする。検査対象内から始まり参考文脈へ続く引用は採用する。参考文脈内から始まる候補は対象外とし、担当範囲への付け替えは行わない（担当範囲が自身の参考文脈付きで検出する）。対象外候補は通常一覧に表示せず、診断用に記録する。
- 同じ引用が複数回ある場合は、段落IDと前後の引用で特定する。
- 特定不能な候補は位置特定失敗として保存し、一覧に表示する。開始・終了位置は未確定とし、診断候補を正式な位置へ流用しない。未確定の位置を前提とした自動再確認・許容語抑制は行わず、その状態を記録する。
- 脱字は欠落位置を含む周辺の実在する文字列を引用し、修正案には補った文字を含める。
- 文字位置の単位はUTF-16コード単位に統一し、バックエンドでも同じ換算を行う。絵文字などを含む場合も強調位置がずれないよう検証する。
- 原文のUnicode正規化や空白除去を暗黙に行わない。ファイル先頭のBOMだけを除外し、それ以外はCRLFを含む保存本文のまま照合する。

位置特定失敗の診断：

- LLMが返した引用文字列、段落ID、前後の引用、検索対象範囲、失敗理由（該当なし・複数該当など）を保存する。
- 完全一致失敗時のみ、元の要求で渡した範囲内を対象に、比較専用の文字列へ限定した正規化を適用して候補を探す。保存本文は変更しない。
- 初期の診断変換は改行形式の統一とNFC比較とする。括弧置換、長音・三点リーダの同一視、空白削除、異体字セレクタ除去は初期対象に含めない。変換規則と版を記録する。
- 変換後の一致候補があれば、指定段落に近い候補を最大3件保存する。同順位の候補があることや打ち切り件数も残し、一意な一致と誤認させない。無制限の全文類似検索は行わない。
- 診断候補ごとに原文の文字列、原文側の範囲、適用した変換を保存する。比較文字列から原文への位置対応を保持し、対応不能なら候補位置も未確定とする。
- 診断結果は後日の改善判断だけに使い、強調表示・再確認・本文修正・採用済み位置として利用しない。候補が見つからないことも記録する。

### 6.4 重複統合と許容語の後処理

- 同じ対象範囲の選択済み観点の検査がすべて終了してから統合し、再確認へ進む。観点の一部が失敗した場合は成功分だけで進め、実行は一部失敗とする。
- 統合は同一の検査実行内に限定する。同じ検査実行ID・原稿版・範囲・原文・修正案の候補を重複候補として統合する。別の検査実行（別モデル、別設定、同条件の再実行を含む）の候補とは統合せず、再確認結果や作者の判断も実行間で共有しない。修正案がないものや別の問題を示すものは、範囲の重なりだけで統合しない。
- 検出した観点と元の候補・理由・暫定判定への参照を保持する。後から失敗観点を再試行して同じ候補が出た場合は参照を追加し、再確認済みの同じ候補を重複実行しない。
- 許容語はプロンプトのヒントとして渡す。後処理では、位置確定済みの「誤字・表記の訂正」候補で、変更が登録語の表記を別表記に置き換えることだけに限定される場合に抑制する。
- 判定条件は「引用内の登録語の出現1箇所を、空でない別の文字列に置き換えるだけで修正案を完全に再現できる」こととする。登録語の外側は原文と完全一致していなければならない。置き換え後の文字列は登録語の一部を残してよく、登録語内の部分的な表記訂正（例：登録語「リュシア」に対する修正案「ルシア」）も抑制の対象になる。引用内に登録語が複数回現れる場合は各出現について判定し、いずれか1箇所の置き換えで再現できれば抑制する。
- 判定のため、引用内の登録語の出現位置と、引用と修正案の差分範囲（共通接頭辞・接尾辞の除去など）を内部で計算する。画面に文字単位のdiffを表示しないこととは矛盾しない。引用が登録語だけという理由や、変更の一部に登録語を含むという理由では抑制しない。差分が登録語の出現範囲の外に及ぶ場合、登録語を削除する場合、複数の出現にまたがる場合は抑制しない。
- 文脈上の誤用、助詞・係り受け、不明瞭な分類、修正案なし、位置特定失敗、複数の変更を含む場合は自動抑制しない。判別に迷う場合は候補を残す。
- 抑制候補は削除せず、適用した登録語と規則・版を保存する。通常一覧では非表示とし、切り替えて確認・採否記録できる。再確認は「許容語により対象外」として扱い、完了済みと混同しない。

### 6.5 文脈を広げた再確認

6.4で統合・許容語後処理を終えた位置確定済み候補ごとに、元の対象範囲に加えてより広い前後の本文を渡し、新しい要求で再確認する。目的は指摘の妥当性の検証とする。再確認にも固有ID、処理状態、試行回数、失敗理由を持たせる。

確認内容：

- 文脈に照らして実際に誤りまたは不自然さがあるか。
- 意図的な口語、省略、倒置、比喩などとして成立しないか。
- 修正案が意味や口調を変えていないか。
- 不要な推敲提案になっていないか。

判定は「指摘を維持」「指摘を撤回」「作者への確認事項」とする。追加の再確認ループは行わない。再確認は修正案を改訂しない。問題は実在するが修正案が不適切と判断した場合は「作者への確認事項」とし、元の修正案は履歴に残すが有効な修正案としては表示しない。撤回した候補も品質評価用に保存し、通常の一覧からは非表示とするが、表示を切り替えて確認できるようにする。

文脈が足りず判断できない場合は確定的に扱わず、作者への確認事項にする。再確認の無効化や失敗は、指摘の正しさの判定と混同しない。


## 7. LM Studio接続

- 接続はバックエンドから行い、ブラウザはバックエンドに接続する。
- OpenAI互換APIを第一候補とする。
- 接続先の設定値はLM Studioのルート（初期候補は `http://127.0.0.1:1234`）とし、パスはアプリ側で組み立てる。ロード状態の確認に使う `GET /api/v0/models` が `/v1` の下にないため。実際のLM Studio設定と実行環境（Windows／WSL）に合わせて変更可能にする。
- モデル一覧の取得はLM Studio固有の `GET /api/v0/models` を正本とし、生成は `POST /v1/chat/completions` を利用する設計とする。`state`、`quantization`、`loaded_context_length` を実行記録に保存し、モデル種別（`llm`、`vlm`、`embeddings` など）で生成に使えるモデルを絞る。OpenAI互換の `GET /v1/models` はロード状態と種別を返さないため併用しない。
- 未ロードのモデルに生成要求を送らない。モデル名を指定した生成要求はLM Studio側のJITロードを起こし、LM Studio既定のコンテキスト長でVRAMが溢れることがある（`docs/decisions/0003-lm-studio-connection.md`）。接続確認、検査の開始、再開、各生成要求の直前に `state` を確認し、`not-loaded` なら要求を送らずに「LM Studio側でモデルをロードしてください」と案内して待機する。実行中にアンロードされた場合も同様に扱い、当該処理を失敗にせず未完了のまま残す。
- 接続確認ではモデル一覧の取得、ロード状態、小さな生成要求の成功を区別して表示する。小さな生成はロード済みのときだけ送り、ウォームアップに利用する。準備待ちを含むタイムアウトと通常検査のタイムアウトを分ける。
- タイムアウトは小さな生成だけで決めず、代表的な入力長・出力長・推論モードの検査でも測定して余裕を設ける。LM Studioの設定によるJITロードやアンロード後の再ロードが起こり得ることを考慮する。
- 構造化出力の対応を実際のモデルで確認し、対応時は `response_format` の `json_schema` を指定する。対応しない場合はJSON出力指示とアプリ側の形式検証を利用する。いずれも受信データのスキーマを検証する。スキーマの `description` がモデルに渡らない構成があるため（検証した構成で確認）、各項目の意味と修正案の粒度はプロンプト本文にも明記する。
- 思考モデルでは、思考の有無を生成設定として `reasoning_effort` で指定し、実行記録に保存する。`max_tokens` は思考分を含めて配分する。
- 応答の本文をまずそのままJSON解析する。失敗した場合だけ、実測で確認したモデル・ランタイムの出力形式に限定して、JSON外側の思考部分を分離して再解析する。JSON文字列内の `<think>` などを一律に削除しない。対応形式を特定できない場合は形式不正とする。
- 形式不正は限定回数で再要求し、修復不能なら失敗として残す。正常な空配列に置き換えない。
- 初期案として自動再試行は各処理1回までとし、その後はユーザーが再試行できるようにする。
- 接続失敗、モデル未準備、入力上限超過、タイムアウト、出力打ち切り、形式不正を区別する。`finish_reason == "length"` は出力打ち切りとして扱い、JSONが解析できても成功扱いしない。終了理由だけでなく、通信の完了とデータの完全性も確認する。
- 入力上限超過時に本文を黙って切り捨てない。設定変更を案内し、未完了範囲を残す。
- モデルのロード方針や入れ替えはMVPではLM Studio側で管理する。アプリは生成要求に伴う準備待ちに対応するが、独自のモデル管理機能は持たない。

本節の接続設計は、検証した構成（`docs/decisions/0003-lm-studio-connection.md`）で疎通を確認済み。他のモデル・ランタイム・ネットワーク構成での挙動は保証しない。

## 8. 保存と実行管理

### 8.1 保存する情報

| 単位 | 主な項目 |
| --- | --- |
| 原稿版 | ID、原稿名、本文、本文ハッシュ、作成日時 |
| 検査実行 | ID、原稿版ID、モデルID、接続先、生成設定、分割設定、許容語一覧・規則版、プロンプト版、開始・終了日時、状態 |
| 検査単位 | ID、対象範囲、観点、処理状態、試行回数、失敗理由 |
| 再確認単位 | ID、統合候補ID、入力範囲、処理状態、試行回数、失敗理由、対象外理由 |
| 位置診断 | 候補ID、LLMの引用、失敗理由、検索範囲、変換規則・版、診断候補の原文・範囲、候補なし・複数候補の状態 |
| 指摘 | ID、原稿版ID、検査実行ID、元候補への参照、分類、段落ID、位置特定状態、開始・終了位置（未確定可）、引用、修正案、理由、初回判定、再確認結果、許容語抑制理由 |
| 作者の判断 | 指摘ID、採否、任意メモ、更新日時 |

APIキーを検査履歴に含めない。再確認前の候補と撤回理由も保存し、再確認による見逃し増加を評価できるようにする。

### 8.2 中断と再開

- 初回検査・再確認の状態遷移、候補の統合・抑制、診断結果、採否の変更を永続化する。
- ブラウザを閉じても、バックエンドが動作している限り処理を継続する。
- 停止操作では新しい要求の送信を止める。実行中の要求を即時中断できない場合は、その状況を表示する。
- バックエンド終了時は完了分を保持し、再起動後に未完了分を再開できる。
- 「再開」と「新規検査の開始」を区別する。再開は既存の実行IDの続きとし、未完了の初回検査・再確認から進める。再開では原稿版、モデル、設定（許容語を含む）、プロンプト版を変更できない。変更する場合は新規検査として開始する。
- 新規検査の開始は、原稿版と設定が既存の実行と一致していても常に新しい実行IDを作る。10節の同条件での複数回実行はこの経路で行う。同条件の既存実行があることは表示してよいが、開始を拒否したり既存実行の再開に置き換えたりしない。
- 二重送信の防止は要求の同一性で判定する。同じ実行IDへの再開要求や、同じ開始操作の重複送信（複数タブ、連打など）を重複登録しない。原稿版と設定の一致は二重送信の判定に使わない。同一処理を同時に取得・実行しない。
- クライアント側のタイムアウトや停止が、LM Studio側での生成終了を意味するとは限らない。前の生成が継続している可能性がある場合は、終了を確認できるまで後続生成を送信せず、再試行の重複を防ぐ。
- 検査・再確認のタイムアウトは、超えた時点で直ちに打ち切る上限ではなく、超えた時点で「生成が遅延している」と通知する閾値とする。超過後も、次項の終了確認の待機の上限内で応答を待ち続け、届いた応答は遅延通知の有無にかかわらず通常どおり結果として採用する（成功、出力打ち切り、形式不正などの判定も届いた内容で行う）。
- 終了確認の待機には上限を設ける。上限を過ぎても確認できない場合は自動で送信を再開せず、実行を「復旧待ち」とし、「生成の停止を確認できません。LM Studio側を確認して再開してください」と表示して手動再開を待つ。時間経過を終了の証拠とみなさない。
- OpenAI互換APIにはキャンセル手段がないため、MVPではHTTP接続の切断をキャンセル要求として扱う。切断で生成が停止することを実環境で確認できた場合に限り、その挙動に基づく自動復旧を検討する。専用SDKのキャンセル機能への切り替えはMVPに含めない。
- 完了済み処理は通常の再開で繰り返さない。失敗した処理を個別に再試行できる。
- 「完了」「一部失敗」「停止中」「実行中」を区別する。未処理範囲がある状態を「問題なし」と表示しない。

保存形式はSQLite、フレームワークは決定済み（`docs/decisions/0001-tech-stack.md`）。保存済み結果の再閲覧はMVP必須とし、可搬用の一括エクスポート形式は実装設計時に決める。

## 9. 非機能要件

- 原稿と検査結果はローカルに保存し、通常動作で外部サービスへ送信しない。
- 初期設定ではWebアプリをループバックアドレスのみで待ち受ける。
- 原稿本文やモデル出力はHTMLとして実行せず、テキストとして表示する。
- 1万字程度の原稿を主な評価対象とする。上限と所要時間は実測後に決める。
- 進捗は完了した検査単位数と再確認件数を表示し、根拠のない残り時間を示さない。
- エラーや中断があっても、原稿と保存済み判断を失わない。
- 原文表示と位置情報の対応を保ち、将来の編集機能の追加に備える。

## 10. 評価方法

過去の原稿に実在した誤字・脱字と、誤検出してほしくない正常な文章を用意する。意図的な口語、省略、倒置、造語、同じ語の反復も含める。評価用原稿は作者が利用を認めたものを用いる。

| 指標 | 確認内容 |
| --- | --- |
| 誤りの検出率 | あらかじめ確認した誤りのうち何件を拾えたか |
| 誤検出 | 正常な箇所への指摘件数と、全指摘中の割合 |
| 修正案の妥当性 | 意味や文体を保ち、最小限の修正になっているか |
| 人間の確認負担 | 1万字の指摘を確認し終えるまでの時間 |
| 実行性能 | 総所要時間、要求数、失敗数 |
| 位置の正確さ | 指摘と強調表示が原文上で正しく対応するか |
| 位置特定失敗 | 全候補中の失敗率、失敗理由、診断変換別の候補取得件数と人間が確認した対応の正誤 |
| 許容語の抑制 | 抑制の適否と、正しい指摘を抑制していないか |

誤字・脱字と、日本語の不自然さは別々に集計する。正常な文章への誤検出と、実際に問題はあるが修正案が不適切なケースも区別する。

同じ原稿・モデル・生成設定で、現在の全文チャット方式、分割方式、分割＋再確認方式を比較する。再確認が正しい指摘を撤回していないかも調べる。調整用の原稿と最終確認用の原稿を可能な範囲で分ける。

比較実験ではモデルに適した生成設定を固定し、temperature 0を全モデルに必須としない。seedは対応する場合に固定し、対応可否も記録する。モデルの識別情報・量子化、LM Studioとランタイムの版、推論モード、プロンプト版など、取得可能な実行条件を保存する。同じ設定でも非決定性が残るため複数回実行し、結果のぶれを併記する。

近似一致は位置の自動確定に使わない。診断候補の正誤と変換別の救済可能件数を人間が評価し、将来導入する場合は誤割り当て率を独立した指標にする。

精度の数値目標は、初回評価の結果を見て決定する。機能の完成と、実用上十分な校正品質が得られたことは別に判定する。

## 11. MVPの受け入れ条件

- [ ] 実際のLM Studio環境でモデルを選択し、生成要求と結果取得ができる。
- [ ] 貼り付けとUTF-8テキスト読み込みの両方から検査できる。
- [ ] 全本文が検査対象として割り当てられ、選択した観点ごとの処理状態を確認できる。
- [ ] 前後の参考文脈を付けた分割検査と、文脈を広げた再確認が動作する。
- [ ] 再確認の有無を切り替えて比較でき、撤回候補も確認できる。
- [ ] 指摘から原文の該当箇所に移動し、正しい範囲が強調される。
- [ ] 同一引用の反復、段落境界、CRLF、異体字セレクタ、結合文字、絵文字を含む原稿で位置がずれず、書記素クラスタの途中で分割されない。
- [ ] 短い会話段落が連続しても文字数基準の参考文脈が渡される。
- [ ] 位置特定失敗が一覧に表示され、LLMの引用と診断候補（または候補なし）が保存される。診断候補は正式な位置に割り当てられない。
- [ ] 許容語による表記訂正の抑制が機能し、登録語内の部分的な表記訂正も抑制され、文法・文脈上の問題は抑制されず、抑制候補を再閲覧できる。
- [ ] 重複統合後に再確認され、初回判定を保持したまま最終判定が表示される。作者の採否は上書きされない。
- [ ] 採用予定・却下・保留を変更して保存でき、本文は変化しない。
- [ ] ブラウザの再読み込み後も結果と判断が保持される。
- [ ] 中断後に初回検査・再確認の未完了分を同じ実行IDで再開でき、失敗を指摘ゼロと誤表示しない。
- [ ] 同じ原稿版・設定で新規検査を開始すると別の実行IDになり、指摘・再確認結果・採否が実行間で混ざらない。
- [ ] 複数タブ・複数原稿の操作でもLLM生成要求がバックエンド全体の単一キューで処理される。
- [ ] 参考文脈内から始まる候補は採用されず診断記録に残り、検査対象内から始まり参考文脈へ続く引用は採用される。
- [ ] 生成終了を確認できない場合に「復旧待ち」となり、自動で後続生成を送信しない。
- [ ] 不正JSON、存在しない引用、出力打ち切りを検知でき、JSON内の `<think>` などの引用文字列を破壊しない。
- [ ] 本文と指示の区切り、非追従の指示、出力検証を実装し、命令文を含む原稿での逸脱を評価・記録する。あらゆるインジェクションの防止を合格条件にはしない。
- [ ] 実原稿で評価指標を記録し、品質上の制約を確認できる。

## 12. 次段階への拡張

次段階では、修正案の適用、本文上の手動編集、diff表示、取り消し・やり直し、修正済み本文のコピー・保存を検討する。

そのためMVPから原稿版と指摘の対象範囲を保存し、修正案と採否を別々に管理する。将来、本文を変更したときは、重なる指摘や位置が変化した指摘を古い状態のまま適用しない仕組みが必要になる。

辞書参照、ルール検査、複数モデル化は、MVPで確認した見逃しや誤検出に応じて追加する。作品全体の整合性検査は別の機能拡張として扱う。
