# UI の見直し：設計（PR14a〜PR14c）

作成日：2026-10-02
状態：設計（ユーザー承認済み。各 PR の詳細計画は着手時に書く）
仕様：`docs/spec/mvp-spec.md`（v0.9.3）5.3、5.4、6.4、9
前提：`docs/experiments/2026-10-02-browser-check/`（実ブラウザでの通し確認。見つけたことの 5・6）、
`docs/plans/2026-09-11-pr12a-result-view.md`（結果画面の正本）、
`docs/plans/2026-09-11-pr12b-run-control.md`（進捗と実行制御の正本）

## 目的

次の 2 つを、機能を増やさずに行う。

- **結果画面での校正作業を楽にする。** 利用者は本文を頭から読み進め、強調された箇所に来たら
  指摘を開いて採否を付ける（2026-10-02 にユーザーが選んだ作業の順）。本文を主役にし、
  強調を選んだらすぐ詳細と採否が見える配置にする。
- **全画面の見た目をそろえる。** アプリ名「朱点」に合わせ、朱筆（校正の赤字）を基調にする。

## 今の画面の問題（実ブラウザでの確認から）

1. 強調を選んでも、詳細と採否は右の列の一覧の一番下に出る。右の列を下までスクロールしないと
   見えない。本文を読みながら進める作業では、これが一番の障害になる。
2. 右の列で絞り込みが上半分ほどを占め、1920×856 程度の画面で指摘は 4 件ほどしか見えない。
3. ページ自体も縦にスクロールし、本文の列・右の列と合わせて、スクロールする領域が 3 つある。
4. 同じ範囲で修正案だけが違う指摘が、一覧に 2 件並ぶ。仕様 6.4 節の統合規則（範囲・原文・修正案が
   同じ候補だけを統合する）どおりの動作だが、同じ箇所を 2 回見ることになる。
5. 配色と部品の形が画面ごとに少しずつ違う。

## 検討した案と決めたこと

| 論点 | 検討した案 | 決めたこと |
| --- | --- | --- |
| 詳細の置き場所 | A. 右の列の上に固定／B. 本文の上に吹き出し／C. 右の列をタブで切り替え | **A**。B は本文を読む流れに最も合うが、仕様 5.3 節（右側に一覧と詳細）の改訂が要り、位置が特定できなかった指摘のために右側の詳細も別に要る。A で一番の問題（問題 1）は解消し、B に必要な右側の詳細も A で作るので、A から始めて、使ってみて目線の移動が気になれば B を足す |
| 表示方式の切り替え | 3 案とも作り、設定で切り替える | 今は作らない。機能の追加にあたり、1 つを使ってみないと何が合うかも分からない |
| 前・次の指摘への移動 | 詳細に「前の指摘／次の指摘」を置く | 作らない。本文を読みながら進めるなら次の指摘へは本文側で移る。必要になったら足す |

| 見た目 | 1. 今の延長（白地・青）／2. 朱筆（白地・朱・本文明朝）／3. 紙と墨（生成り地・墨・本文明朝） | **2** |

## 1. 結果画面の配置（PR14a）

### ヘッダー（上部）

- 1 行にまとめる。原稿名、状態、検査と再確認の「完了 n / 全 m 件」、停止・再開のボタンを並べる。
- 観点別の内訳（失敗・処理中・未処理・対象外）は「詳しい進捗」で開く折りたたみにする。
  仕様 5.3 節の「上部：観点別の処理進捗」は、この折りたたみの中に残すことで満たす。
- 案内文（停止中、遅延、復旧待ち、失敗した単位）は、出るときだけヘッダーの下に出す。
  文言と出す条件は変えない。

### スクロール

- ページ全体はスクロールさせない。主な領域は本文の列と右の列の 2 つにする。
- 右の列の中では、高さを固定した詳細と、その下の絞り込み＋一覧が、それぞれの中でスクロールする。
  解消したいのは、ページ自体のスクロールが本文や一覧のスクロールと入れ子になり、詳細が画面外へ流れることで
  （問題 1・3）、右の列の中で詳細と一覧が別々にスクロールすることは問題にしない。詳細は高さを固定するので、
  一覧をスクロールしても詳細の位置は動かない。
- ヘッダーと案内文の高さが変わっても、2 つの列が残りの高さに収まるようにする
  （今の `calc(100vh - 3.5rem - …)` のような固定値の引き算をやめ、縦方向の flex で埋める）。

### 右の列

上から順に、詳細、絞り込み、一覧と並べる。

- **詳細**：右の列の上部に固定し、一覧をスクロールしても動かない。長いときは詳細の中だけで
  スクロールし、高さは列のおよそ半分を上限にする。指摘を選んでいないときは
  「本文の強調か一覧から指摘を選んでください」と出す。中身（5.4 節の全項目）は変えない。
- **絞り込み**：「絞り込み（31 / 33 件を表示中）」の 1 行に折りたたむ。開くと今の項目がすべて出る。
  既定の状態から変えているときは、閉じていても「絞り込み中」と分かる表示にする。
- **一覧**：今の並び順（本文の位置順）と項目のまま。

### 選択の動き

- 本文の強調を選ぶと、右上の詳細が切り替わり、一覧の該当行が選択状態になって、
  見える位置までスクロールする。
- 一覧から選ぶと、本文が該当箇所までスクロールして強調される（今と同じ）。

### 変えないもの

本文の描き方、強調の付け方、位置が特定できなかった指摘の扱い（強調せず、検査対象範囲への移動だけ）、
採否の保存、SSE による更新、各案内文の文言。

## 2. 同じ範囲の指摘のまとめ（PR14b）

- **まとめる条件**：位置が確定していて、範囲（UTF-16 の開始と終了）が完全に一致する指摘だけをまとめる。
  一部だけ重なる指摘と、位置が特定できなかった指摘はまとめず、1 件ずつ扱う。
- **表示だけの変更である。** 仕様 6.4 節の統合規則、保存の単位、採否の単位、件数の数え方、
  評価とエクスポートは変えない。
- **一覧**：まとめた指摘は 1 行で表し、原文の引用に「2 案」のような件数を添える。分類と採否は、
  全員が同じなら 1 つ、違えば「文法・助詞」「未判断 1・却下 1」のように並べる。並び順は本文の位置順。
- **詳細**：まとめた指摘を全部縦に並べる。それぞれに修正案・理由・判定・再確認の状態・採否・判断メモを持ち、
  採否も 1 件ずつ付ける。
- **絞り込みとの関係**：まとめるのは、絞り込みを通った指摘の中だけ。同じ範囲でも絞り込みで隠れた指摘は、
  詳細の末尾に「絞り込みで非表示：1 件」とだけ出し、採否の操作は付けない。
- **件数**：「31 / 33 件」は指摘の件数で数える（まとめた行の数ではない）。
- **重なる指摘**：一部だけ重なる指摘は、今の「重なる指摘」のリンクのまま残す。
- **選択**：まとめた行を選ぶと、まとめの先頭（本文の位置順で最初、同順なら今の並び順で最初）の指摘を
  選択中とする。本文の強調から選んだときも同じ。
- **選択中の指摘が絞り込みから外れたとき**：今の結果画面は、採否の保存などで選択中の指摘が絞り込みから
  外れると選択を外す。まとめの中では、これだけだと困る。たとえば採否を「未判断」だけに絞り、同じ範囲に
  未判断の指摘が 2 件あるまとめで先頭を「却下」にすると、2 件目がまだ表示対象なのに詳細全体が閉じる。
  そこで、選択中の指摘が絞り込みから外れたとき、同じまとめ（位置が確定し、範囲が完全に一致する指摘）で
  絞り込みを通っている指摘が残っていれば、その先頭へ選択を移す。残っていなければ、今どおり選択を外す。
  PR14b の計画には、採否・分類・再確認状態の各絞り込みで、まとめの先頭だけが外れる場合のテストを入れる。

まとめる処理（範囲の一致判定、絞り込みとの関係、行ごとの分類・採否の要約）は、DOM を持たない
純粋な関数として `features/results/` に置き、単体テストで境界を押さえる。

## 3. 見た目の朱筆化（PR14c）

### 色

| 役割 | 値 | 根拠 |
| --- | --- | --- |
| アクセント（文字・ボタン） | `#c23a22` | 白地とのコントラスト比 5.35（文字の基準 4.5 を満たす） |
| アクセント（線・下線・枠） | `#d9452b` | 白地との比 4.34（線の基準 3 を満たす） |
| エラー | `#9f1239`（臙脂） | 白地との比 8.02 |
| 地・文字 | 白、今の墨に近い黒（`#1a1a1a`） | 変えない |

- **エラーは色だけで見分けない。** 枠で囲み、先頭に「エラー」と書く。朱は「指摘・操作」、
  臙脂の枠は「エラー」と役割を分ける。
- 本文の強調は、指摘箇所に朱の下線、選択中の箇所に薄い朱の地を敷く。今の黄色の地と青の選択色はやめる。

### 書体

- 本文の列だけ明朝体にする（游明朝、ヒラギノ明朝、Noto Serif JP の順に探し、無ければ serif）。
- 詳細欄の「原文」と「修正案」も明朝体にして、本文と見比べやすくする。
- それ以外はゴシックのまま。

### 部品

- ボタンは 2 種類。主な操作（検査を開始する、保存など）は朱の塗り、それ以外は枠だけ。
- 入力欄・カード・見出し・案内文の形を全画面でそろえる。

### 対象と方法

- 対象はヘッダー、原稿と検査設定（トップ）、設定、実行一覧、結果画面の 5 つ。
- `styles/tokens.css` の変数を差し替え、各画面の CSS Modules を書き直す。新しいライブラリは入れない。
- 各画面の項目、文言、動きは変えない。

## 対象外（MUST NOT）

- 機能を増やさない。表示方式の切り替え、前・次の指摘への移動、キーボード操作、ダークモードは作らない。
- 仕様書を改訂しない。5.3 節の各項目（上部の観点別の進捗、左の本文、右の一覧と詳細、絞り込み、
  同じ範囲の指摘をすべて参照できること）は、折りたたみやまとめ表示の形ですべて残す。
- サーバーの API と DTO を変えない。3 本とも `packages/web` だけの変更にする。
- 仕様 6.4 節の統合規則、保存の単位、件数の数え方を変えない。
- 本文をブラウザで加工しない、`dangerouslySetInnerHTML` を使わない（PR12a の制約のまま）。
- CSS フレームワークや UI ライブラリを入れない（PR11 決定 4・5 のまま）。

## 進め方と確かめ方

- **順番**：PR14a（配置）→ PR14b（まとめ）→ PR14c（朱筆）。配置を先に固めてから見た目を塗り替えると、
  CSS の書き直しが 1 回で済む。3 本とも単独でマージできる形にする。
- **詳細計画**：各 PR の着手時に `docs/plans/` に詳細計画を書く（この設計書を前提にする）。
- **テスト**：まとめる処理は純粋な関数の単体テスト、折りたたみ・詳細の固定・選択の動きは DOM テストで
  確かめる。各 PR で `pnpm check` を通す。
- **画面での確認**：各 PR で、WSL2 上のサーバーと Chrome を実際の LM Studio につなぎ、評価原稿で通して
  確かめる（`docs/experiments/2026-10-02-browser-check/` と同じ手順）。理由や判断メモが長い詳細と、件数の多い
  一覧が同時にある状態も含める。WSL2 には日本語フォントが無く、
  明朝体と朱の見え方は正しく出ないので、PR14c は Windows のブラウザでユーザーが確かめる。
- **実装の分担**：実装とテストの生成は qwen に委譲し、設計・レビュー・確認は Claude が行う
  （`CLAUDE.md`）。
