# PR10 詳細計画：HTTP API と SSE（server）

作成日：2026-09-09
状態：計画済み（タスク分解まで）
仕様：`docs/spec/mvp-spec.md`（v0.9）4、5.1、5.2（初期値）、8.2（ブラウザを閉じても継続、再開と新規の区別、二重送信）、9（ループバック、テキストとして扱う）、11 節（2・12・13 項）
前提：`docs/plans/2026-09-07-mvp-roadmap.md` の PR10 節、`docs/reference/invariants.md`、
`docs/plans/2026-09-09-pr9-orchestration.md`（決定 1〜23）、`docs/plans/2026-09-09-pr9b-orchestrator.md`（決定 24〜45）

## 目標

PR9b までに関数として動いているオーケストレーター・永続化層・LM Studio クライアントを、
ブラウザ（PR11・PR12）から呼べる HTTP API と SSE にする。すなわち、

- `/api/` 配下の JSON API（接続設定と接続確認、原稿、実行の開始・停止・再開・再試行、指摘、採否、復旧確認）
- `/api/runs/:id/events` の SSE（進捗通知。状態の正本は DB）
- UI から接続先を上書きする `settings` 表と、実行中に接続先が変わらない仕組み
- graceful shutdown と `LmStudioClient.close()`（PR7・PR8 からの持ち越し）
- PR11・PR12 が import する要求・応答の型と zod スキーマ（`packages/shared/src/api/`）

本 PR の成果物は「画面が依存する契約」である。エンドポイントの一覧と DTO の形を本書で固定し、
PR11・PR12 はこれを読んで作る。

## 対象外（MUST NOT）

- **画面を作らない**（PR11・PR12）。
- **エクスポート（`GET /api/runs/:id/export`）を作らない**（PR13。決定 16）。
- **オーケストレーターの実行の意味を変えない。** 状態遷移表、復旧待ちの規則、再開・再試行の受け付け条件は
  PR9 の決定のまま。本 PR が足すのは判別子・接続の供給元・実行中判定の 3 点だけ（決定 6・7・10）。
- **接続断で `failed` になった単位を `pending` に戻さない**（決定 17。決定 20 の改訂は持ち越しのまま）。
- **API キーを DB に保存しない。応答・ログ・SSE・エラーメッセージに API キーを出さない。接続先 URL は
  `GET/PUT /api/settings/connection` の応答（利用者が設定を見る場所）にだけ出し、実行・指摘・単位・SSE・
  エラーの本文には出さない。**
- **本文を加工しない。** 貼り付けはブラウザから受け取った文字列をそのまま、ファイルは `ingestUtf8Bytes`
  （BOM 除外のみ）の結果をそのまま保存する。
- **本文を書き換える経路を作らない。** 採否は `judgments` への記録だけ。
- **サーバー側の絞り込み・ページングを作らない**（決定 15）。
- **サービス層を作らない**（決定 1）。
- **Hono RPC（`hc`）を使わない**（決定 2）。
- CORS を設定しない（vite の dev server が `/api` を proxy し、本番は同一オリジンで静的配信する）。

## 全体の制約（不変条件から）

- 待ち受けは既定で `127.0.0.1`（`config.ts` のまま）。
- API キーを検査履歴・ログ・結果出力に含めない。**接続先 URL は接続設定の応答以外に出さない**
  （`runs.endpoint_url` に保存するだけで、`RunDto` には載せない。PR9b 決定 24）。
- SSE は通知手段。状態の正本は DB。ブラウザ切断で検査を止めず、再接続時は API で状態を取得して復元する。
- 「再開」は既存の実行 ID の続き、「新規検査の開始」は常に新しい実行 ID。二重送信の防止は
  `startOperationId` の同一性で判定する（PR9b 決定 12）。
- LLM 生成要求はバックエンド全体で単一キュー、同時実行数 1。**HTTP 層は生成要求を送る経路を新設しない**
  （接続確認も試験生成を送らない。決定 8）。
- 未ロードのモデルに生成要求を送らない。
- 分割範囲と確定位置の正本はサーバーが保存した UTF-16 範囲。API はそれをそのまま返す。
- 失敗・形式不正を指摘ゼロに置き換えない。実行の `status` / `stopReason` と単位の `failure` を落とさずに返す。
- 依存の版は完全固定。相対 import は `.ts` 拡張子付き。scripts は Windows で動く書き方。
- 公開リポジトリ。個人情報・機器固有の値・実原稿をコミットしない。

## エンドポイント

すべて `/api/` 配下、要求・応答は JSON（アップロードのみ multipart、`events` のみ SSE）。
エラーは 1 形式 `{ error: { code: string; message: string } }`（決定 4）。

| メソッド・パス | 要求 | 応答 | 状態コード |
| --- | --- | --- | --- |
| `GET /api/settings/connection` | — | `ConnectionSettingsDto` | 200 |
| `PUT /api/settings/connection` | `PutConnectionRequest` | `ConnectionSettingsDto` | 200 / 400 `validation` / 409 `runs-active` |
| `POST /api/settings/connection/check` | `ConnectionCheckRequest` | `ConnectionCheckDto` | 200（到達不能も 200 で `reachable: false`） |
| `POST /api/manuscripts` | `CreateManuscriptRequest` | `ManuscriptVersionDto` | 201 / 400 `validation` `empty-body` `malformed-body` |
| `POST /api/manuscripts/upload` | multipart：`file`（バイト列）、`name` | `ManuscriptVersionDto` | 201 / 400 `validation` `invalid-utf8` `empty-body` `malformed-body` |
| `GET /api/manuscripts/:id` | — | `ManuscriptVersionDto` | 200 / 404 |
| `GET /api/runs` | — | `RunSummaryDto[]`（開始日時の降順） | 200 |
| `POST /api/runs` | `StartRunRequest` | `RunDto` | 201（新規）/ 200（同じ `startOperationId` の既存）/ 400 `validation` `invalid-run-settings` / 404 `not-found`（原稿版） |
| `GET /api/runs/:id` | — | `RunDetailDto` | 200 / 404 |
| `GET /api/runs/:id/units` | — | `RunUnitsDto` | 200 / 404 |
| `POST /api/runs/:id/stop` | — | `{ run: RunDto }` | 202 / 404 / 409 `run-not-active` |
| `POST /api/runs/:id/resume` | — | `{ run: RunDto }` | 202 / 404 / 409 `run-rejected-<reason>` |
| `POST /api/runs/:id/retry-failed` | `RetryFailedRequest` | `{ run: RunDto }` | 202 / 400 `validation` `invalid-retry-target` / 404 / 409 `run-rejected-<reason>` |
| `GET /api/recovery` | — | `RecoveryDto` | 200 |
| `POST /api/recovery/confirm` | `ConfirmRecoveryRequest` | `RecoveryDto` | 200 / 400 `validation` |
| `GET /api/runs/:id/findings` | — | `FindingDto[]`（`listFindings` の並び：本文位置 `start` 昇順、位置未確定は最後、同順位は `createdAt` → `id`） | 200 / 404 |
| `GET /api/findings/:id` | — | `FindingDetailDto` | 200 / 404 |
| `PUT /api/findings/:id/judgment` | `PutJudgmentRequest` | `JudgmentDto` | 200 / 400 `validation` / 404 |
| `GET /api/runs/:id/events` | — | SSE（決定 12） | 200 / 404 |
| `GET /api/health` | — | 既存のまま | 200 |

補足：

- `POST /api/runs` の 201 は**作成直後のスナップショット**である。`startRun` は生成要求を送らずに同期で
  返り、ループは次のマイクロタスクから走るので、モデル未ロードや復旧ゲート閉鎖による停止は 201 の時点では
  まだ `running` で、SSE か `GET /api/runs/:id` で分かる。201 の時点で終端状態なのは開始計画で判明するもの
  （入力上限超過など）だけ（決定 14）。
- `stop` / `resume` / `retry-failed` の 202 は「受け付けた」であり、実行の結末は SSE または
  `GET /api/runs/:id` で追う。
- 404 の判定はハンドラーが `findRun` / `findManuscriptVersion` / `findFinding` で行う（決定 10）。
- `POST /api/runs` の 200 / 201 の判別は、`startRun` を呼ぶ前に `findRunByStartOperationId` で既存の有無を
  見て決める（`startRun` の戻り値だけでは新規か既存かが分からない）。**この判定は他の入力の検証より先**
  （決定 14 の順序）。

## DTO（`shared/src/api/dto.ts`）

原則（決定 3）：

- 日時は ISO 8601 文字列（`Date.toISOString()`）。
- `RunRecord` → `RunDto` は `endpointUrl` と `startOperationId` を落とし、日時を文字列にするだけ。他は同名。
- レコードにあって DTO に無い項目は「内部でだけ使う値」である。DTO に足すときは本書を改訂する。

## 要求（`shared/src/api/requests.ts`）

zod 4 で書き、`z.infer` した型を同じファイルから export する。**構文的な検証だけ**を zod で行い、
意味的な検証（分割設定の整合、再試行対象の妥当性）は既存の関数（`validateChunkSettings`、
`retryFailedUnits`）に任せて、その例外を 400 に写す（決定 4）。

## 設計上の決定

### 決定 1：薄いハンドラーだけを置き、サービス層を作らない

ハンドラーは「zod 検証 → オーケストレーター／リポジトリ呼び出し → DTO 射影 → 状態コード」だけを行う。
オーケストレーターがすでにユースケース層であり、リポジトリ呼び出しも 1〜2 行なので、間にもう 1 層置いても
素通しになる。唯一ハンドラーに収まらない `GET /api/runs/:id` と `units` の組み立ては `api/run-view.ts` に
関数として切り出す（HTTP と無関係なので `app.request` を使わずにテストできる）。

**代案（採らない）**：`server/src/service/` にユースケース関数を並べる。将来ハンドラーが太ったときに
切り出せばよく、今は YAGNI。

### 決定 2：型は `shared` に置き、状態語彙を server から移す

PR11 は「型は `shared` から」（ロードマップ）。DTO は `RunStatus` / `UnitStatus` / `JudgmentStatus` /
`RunStopReason` / `RecheckNotApplicableReason` / `CandidateLocateStatus` / `FindingLocateStatus` /
`ReasoningEffort` を参照するが、これらは現在 server にある。web が `@shuten/server` の型を import すると
`node:*` や `better-sqlite3` の型解決が web の tsconfig に入り込むので、**文字列 union である状態語彙を
`shared/src/run/` へ移し、server は再エクスポートに変える**。前例は `shared/src/run/failure-reason.ts`。

移すのは定数配列と型だけ。遷移表（`run/state.ts`）や意味付けは server に残す。

**代案（採らない）**：Hono RPC（`hc`）。web がサーバーのルート型に直接依存し、ロードマップの
「fetch の薄い包み」と合わない。

### 決定 3：公開 DTO への射影は 1 か所、漏えい検査を 1 本置く

`server/src/api/dto.ts` にレコード → DTO の射影関数を並べる（`toRunDto` など）。`RunRecord` の
`endpointUrl` はここで落ちる。ハンドラーはレコードをそのまま `c.json` に渡さない。

テスト A0（後述）が全エンドポイントの応答・エラー本文・SSE ペイロードを JSON 化し、番兵の接続先 URL
（`http://sentinel.invalid:9`）が現れないことを確認する。**例外は `GET/PUT /api/settings/connection` の
正常応答だけ**（仕様 5.1 が接続先 URL の表示を求める唯一の場所）で、その 2 つも `endpointUrl` 以外の
項目には出ないことを見る。API キーの番兵は例外なく全応答で見る。**新しいエンドポイントを足すときは
A0 に加える**（本書のテスト節に明記）。

### 決定 4：エラーは 1 形式、写像は 1 か所

`api/errors.ts` に `ApiError(status, code, message)` を置き、`app.onError` で `{ error: { code, message } }` に
写す。既知の例外の写像：

| 発生源 | 状態 | `code` |
| --- | --- | --- |
| JSON として読めない本文、空本文（任意でない場合）、`Content-Type` が `application/json` でない | 400 | `invalid-json`（`readJson` が読む場所で写す。500 にしない） |
| zod 検証失敗 | 400 | `validation`（メッセージは不正なパス名の列挙だけ。値は入れない） |
| multipart の項目の型違い（`file` が文字列、`name` が `File`）、同名項目の重複 | 400 | `validation` |
| `MalformedBodyError`（孤立サロゲート。PR8 決定 17） | 400 | `malformed-body` |
| `Utf8DecodeError` | 400 | `invalid-utf8` |
| 空本文 | 400 | `empty-body` |
| `validateChunkSettings`（`InvalidChunkSettingsError`）・`validateHardTimeouts` の違反（決定 14） | 400 | `invalid-run-settings` |
| `RetryTargetError` | 400 | `invalid-retry-target` |
| 対象なし | 404 | `not-found` |
| 再開・再試行の拒否（決定 10） | 409 | `run-rejected-<rejectReason>` |
| `stopRun` の `accepted: false` | 409 | `run-not-active` |
| 実行中の接続設定変更（決定 5） | 409 | `runs-active` |
| その他 | 500 | `internal`（定型文のみ） |

`message` には ID だけを入れ、URL・API キー・原稿の断片を入れない。500 のときサーバーのログには
例外のクラス名とスタックを出すが、`LmStudioError` の `message` は接続先を含みうるので**ログにも出さない**
（PR9 決定 14 の方針を HTTP 層でも維持）。

### 決定 5：接続先 URL は `settings` 表、API キーはメモリ。実行中は変更を拒否する

仕様 5.1 は UI から接続先と API キーを設定できることを求め、ロードマップは「UI 側の値は DB に保存」。

- **URL** は `settings` 表（`key` = `lm_studio_url`）に保存し、起動時に行があれば環境変数より優先する。
  保存済みの値が `parseLmStudioUrl` を通らない（DB を手で編集した）場合は環境変数と同じ扱いで、URL を
  含まない定型文を出して非ゼロ終了する（黙って環境変数に戻さない）。
- **API キー**は保存しない。`PUT` で受け取った値をプロセスのメモリに持ち、再起動後は環境変数
  `SHUTEN_LM_STUDIO_API_KEY` の値に戻る。ローカルの OpenAI 互換サーバーは通常キーなしで使うので、
  「再起動のたびに再入力」が実際に起きるのは認証が必要な環境だけ。その環境では環境変数で渡せる。
- `GET` は `hasApiKey: boolean` だけを返す。
- **検査実行が走っている間（`orchestrator.activeRunIds()` が空でない）は `PUT` を 409 で拒否**し、
  `ConnectionManager.update` を呼ばない。走っている実行の接続先が途中で変わる事故を防ぐ。

`settings` 表は `key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at INTEGER NOT NULL`。PR10 で使う鍵は
1 つだが、表の形は将来の鍵にも使える汎用のままにする（列を足すより安い）。

**代案（採らない）**：キーも DB に平文保存。ユーザーの判断で保存しない。

### 決定 6：オーケストレーターは「接続の供給元」から実行ごとに 1 回読む

`OrchestratorDeps` の `client` と `endpointUrl` を 1 つの `ConnectionSource` に置き換える。

```ts
export interface ConnectionSnapshot {
  readonly client: LmStudioClient;
  readonly endpointUrl: string;
}
export interface ConnectionSource {
  /** 現在の接続。開始・再開・再試行の時点で 1 回だけ読み、その実行に固定する。 */
  current(): ConnectionSnapshot;
}
// OrchestratorDeps: client / endpointUrl → connection: ConnectionSource
```

`startRun` / `resumeRun` / `retryFailedUnits` は `deps.connection.current()` を 1 回呼び、レジストリの
実行エントリに `client` を入れる。**走っている実行は開始時に読んだクライアントを持ち続ける**ので、
「実行中に接続先が変わらない」がオーケストレーター側で閉じる。決定 5 の 409 はその上の二重の防御
（利用者に「今は変えられない」と伝えるため）。

**`runs.endpoint_url` に書くのは `startRun` だけ。** 再開・再試行は現在の `endpointUrl` と保存済みの
`run.endpointUrl` を比較し、**一致しなければ状態を 1 つも変えずに拒否する**（`rejectReason: "connection"`。
決定 10）。一致すれば保存済みの値をそのまま使い、更新しない。停止中に接続先を変えてから再開できると、
同じ実行の前半と後半が別の LM Studio で処理され、しかも保存済み URL を上書きすると前半の接続条件を失う。
接続先の変更を許すには要求または単位ごとに接続先の履歴を持つ必要があり、本 PR の範囲には重すぎる。
利用者は接続先を戻して再開するか、新規検査として開始する（仕様 8.2「再開では…設定を変更できない」の
接続先への適用）。この比較は `hasStaleVersions` と同じ位置（`claimRunChecked` の前）で行う。

`ConnectionManager`（`server/src/connection.ts`）が `ConnectionSource` の実体で、`describe()` と
`update()` を足す。`update` は `parseLmStudioUrl` で検証し、`settings` に書き、新しい `LmStudioClient` を
作って古いものを `close()` する。

既存のオーケストレーターのテストは `client` を渡している箇所を固定値の `ConnectionSource`
（`fixedConnection(client, url)` ヘルパー）に変える機械的な修正になる。

### 決定 7：実行中判定は `activeRunIds()` で公開する

`Orchestrator` に `activeRunIds(): readonly string[]`（レジストリの鍵）を足す。決定 5 の 409 判定に使う。
「走っているか」の正本はレジストリであり、DB の `status = running` ではない（起動時に残った `running` 行は
`reconcileOnStartup` が終端化しているので一致するが、判断の根拠を 1 つにする）。

### 決定 8：接続確認はモデル一覧とロード状態の確認まで。試験生成は送らない

`POST /api/settings/connection/check` は**現在の接続**で行う（URL を試してから保存する経路は作らない。
UI は `PUT` → `check` の順に呼ぶ）。

1. `listModels()`。失敗 → `{ reachable: false, error: { reason, message }, models: [], model: null }`。
   `error.message` は **`reason` ごとの定型文**で、例外の `message` をそのまま入れない
   （`LmStudioError.message` は接続先を含みうる。決定 4）。
2. 到達できたら `models` を返す。
3. 要求に `modelId` があれば一覧から完全一致で探し、`found` / `state` / `loaded` を返す。

**試験生成は送らない。** ロードマップの PR10 節は「小さな生成を区別して返す」としていたが、
接続確認の生成がタイムアウトすると LM Studio 側で生成が続いている可能性が残る（PR9 の「生成終了未確認」）。
実行の生成なら executor が `halt` を立てて復旧ゲートを閉じ、`runs` の行が「何を確認すべきか」を表すが、
接続確認は実行の行を持たないので、ゲートを閉じても復旧確認の対象を表現できず、閉じなければ
不変条件「生成終了を確認できなければ後続生成を送らない」に反する。永続化できる操作 ID・ゲートへの登録・
起動時照合まで作れば解決するが、接続確認のためにその機構を持ち込む価値はない。仕様 5.1 の
「接続確認」と不変条件「接続確認では先に `GET /api/v0/models` で `state` を確認する」は 1〜3 で満たす。
モデルとの実際の相性は、最初の検査実行そのものが確かめる（開始直後の `check-finished` / `run-settled`）。

これにより接続確認はキューも復旧ゲートも使わない。`PUT /api/settings/connection` と確認が重なっても、
`listModels` は古いクライアントで完了し（`Agent.close()` は進行中の要求を流す。決定 19）、競合しない。
ロードマップの PR10 節を更新する。

### 決定 9：設定の初期値は `shared` の定数にし、エンドポイントにしない

`shared/src/api/defaults.ts` に `RUN_SETTINGS_DEFAULTS` を置く。web も server も CLI も import できるので、
`GET /api/settings/defaults` は作らない。

```ts
export const MAX_TIMEOUT_MS = 2_147_483_647;
export const RUN_SETTINGS_DEFAULTS = {
  generation: { maxTokens: 16_000, temperature: 0, reasoningEffort: "none" },
  chunkSettings: {
    targetGraphemes: 1_500, contextGraphemes: 1_000, recheckContextGraphemes: 3_000,
    roundingTolerance: 0.2, maxInputGraphemes: 12_000,
  },
  timeouts: { checkMs: 300_000, recheckMs: 300_000 },
  perspectives: ["typo", "naturalness"],
  recheckEnabled: true,

```

値は CLI の `DEFAULTS`（`cli/src/args.ts`）と同じ。CLI の `DEFAULTS` はこの定数を参照するよう寄せ、
2 か所に書かない。`reasoningEffort: "none"` は決定記録 0003（2026-09-09）の暫定方針による。

### 決定 10：再開・再試行の拒否理由を判別子で返す

`RunLaunchResult` に `rejectReason` を足す（PR9b の持ち越し「拒否理由の判別子」）。

```ts
export type RunRejectReason =
  | "running"        // 走っているループがある（PR9b O11。done はそのループのもの）
  | "settings"       // stop_reason が settings（PR9b 決定 36）
  | "stale-version"  // 版が変わった（PR9b 決定 45-1）
  | "connection"     // 現在の接続先が保存済みの endpoint_url と違う（決定 6）
  | "status";        // その状態からは再開・再試行できない（completed など）
export interface RunLaunchResult extends StartRunResult {
  readonly accepted: boolean;
  readonly rejectReason: RunRejectReason | null;   // accepted なら null
}
```

HTTP は `accepted: false` を 409、`code` を `run-rejected-<rejectReason>` に写すだけで、`settings` 判定や
`hasStaleVersions` を HTTP 層に書き写さない。実行が存在しない場合はオーケストレーターが `Error` を投げる
現状を変えず、ハンドラーが先に `findRun` して 404 にする（同一プロセスなので競合しない）。
`startRun` の原稿版なし（`Error`）も同様にハンドラーが `findManuscriptVersion` で先に弾く。

### 決定 11：復旧確認は API が復旧ゲートを直接使う

「復旧を確認した」操作（PR9b 持ち越し）は `recoveryGate.unblock(runId)` を呼ぶだけなので、
オーケストレーターにメソッドを足さず `api/recovery.ts` がゲートを直接使う。PR9b 決定 24 がゲートを
`index.ts` に置いたのはこのためである。`GET /api/recovery` も `gate.blocked` / `gate.blockedRunIds` を
読むだけ。

`POST /api/recovery/confirm` は実行の状態を変えない（`recovery-waiting` のまま）。再開は別に
`POST /api/runs/:id/resume` で行う。**版が変わった `recovery-waiting` の実行は再開できず終端化もされない**ので、
`reconcileOnStartup` が起動のたびにゲートを閉じ直し、利用者は起動のたびに確認操作をすることになる。
本 PR はそれを「拒否されるだけの再開を試す」から「専用の操作」にするだけで、根本（stale な実行を
終端化する手段）は持ち越す。PR12 はこの操作を「再起動のたびに要る」ものとして表示する。存在しない `runId` を渡されてもゲートの `unblock` は無害なので、
404 にはせず 200 で現在のゲート状態を返す。

### 決定 12：SSE は射影した `RunEventDto` を流し、再送しない

内部の `RunEvent` はそのまま流さない。`check-finished` の `CheckUnitResult` は内部の結果型を丸ごと含み、
将来の変更が線上の契約に直結する。線上には「何が・どうなったか」だけを流し、内容はクライアントが
API で取り直す（不変条件「SSE は通知手段、正本は DB」の素直な形）。

購読の規則（`api/events.ts`。`hono/streaming` の `streamSSE`）：

1. 実行が無ければ 404。
2. **先に hub へ購読してから** DB の状態を読む。終端状態（`status !== "running"`）なら合成した
   `run-settled` を 1 件送って閉じる。`running` ならそのまま流す。この順序で「状態確認と購読の間に決着した」取りこぼしを消す
   （JS は単一スレッドなので、購読後に起きた決着は必ず届く）。
3. `run-settled` を転送したら閉じる。
4. 15 秒ごとに `: ping` コメント行を送る（vite proxy や中継の無通信切断対策）。
5. クライアント切断（`stream.onAbort`）で購読を解除するだけ。**実行は止めない。**
6. 再送はしない（`id:` も付けない）。再接続したクライアントは `GET /api/runs/:id` と `findings` で復元する
   （仕様 8.2）。

`event:` は `RunEventDto.type`、`data:` は JSON 1 行。

**書き込みと終了の機構**（`streamSSE` のコールバックは async で、返るまでストリームが開いている）：

- 購読 1 つにつき `{ onEvent, onClose }` を hub に渡す（決定 13）。コールバックは `closed` という Promise を
  作って await し、`onClose` / `run-settled` の転送後 / `onAbort` / 書き込み失敗のいずれかで resolve する。
  resolve でコールバックが返り、ストリーム本体が完了する。
- `writeSSE()` は Promise を返し、reject は同期の `try/catch` では捕まらない。**購読ごとに 1 本の Promise
  chain を持ち、`onEvent` は `chain = chain.then(() => writeSSE(...))` で直列化する**（イベントが連続しても
  順序が保たれる）。chain の reject は購読解除と `closed` の resolve に写し、以後のイベントは捨てる。
- `: ping` も同じ chain に乗せる（`setInterval` は `closed` で止める）。間隔は注入可能にしてテストで短くする。

PR12 への帰結：`stopped` の実行を購読していたクライアントは合成 `run-settled` で閉じられているので、
`resume` / `retry-failed` を呼んだら**購読し直す**。

### 決定 13：event hub は購読者の例外を握りつぶす

`run/event-hub.ts` の `createRunEventHub()`：

```ts
export interface RunEventSubscriber {
  onEvent(event: RunEvent): void;   // 同期。非同期の書き込みは購読者側が chain に乗せる（決定 12）
  onClose(): void;                  // closeAll から。購読者はストリームを完了させる
}
export interface RunEventHub {
  emit(event: RunEvent): void;
  subscribe(runId: string, subscriber: RunEventSubscriber): () => void;   // 戻り値は購読解除
  closeAll(): void;                 // 全購読者の onClose を呼び、購読を空にする
}
```

`index.ts` が `onEvent: hub.emit` で渡す。`emit` はループから同期に呼ばれるので、購読者の例外を捕まえて
捨てる（投げ返すとループ側で PR9b 決定 33 の内部エラーになり、SSE の不具合が検査を止めてしまう）。
`onClose` の例外も同様に捨てる。`closeAll()` は shutdown（決定 18）から呼ぶ。

### 決定 14：201 は作成直後のスナップショット。二重送信は 200。空本文は原稿の保存で拒否

- `POST /api/runs` の 201 は `startRun` が返した `RunRecord` の射影であり、**その後の結末を含まない**。
  `startRun` は生成要求を送らずに同期で返り、ループは次のマイクロタスクから走る（PR9b 決定 24）ので、
  モデル未ロード（`model-not-loaded`）や復旧ゲート閉鎖（`recovery-blocked`）は 201 の時点ではまだ
  `running` で、直後の `run-settled`（SSE）か `GET /api/runs/:id` で `stopped` になる。
  201 の時点で終端状態なのは、開始計画（`planStart`）で同期に判明するものだけ：入力上限超過
  （`stopped` / `settings`）と、ハンドラーの事前検証をすり抜けた設定不正（同じく `stopped` / `settings`）。
  「失敗を指摘ゼロと誤表示しない」は `status` / `stopReason` を落とさないことで守る。
- **`POST /api/runs` のハンドラーの順序**（仕様 8.2「二重送信の防止は要求の同一性で判定し、条件の一致は
  判定に使わない」を守るため、冪等判定を他の検証より先に置く）：
  1. 本文が JSON のオブジェクトであり、`startOperationId` が有効な文字列（1〜200 文字）であることだけ検証する。
  2. `findRunByStartOperationId` で既存の実行があれば、**残りの入力を検証も比較もせず** 200 で返す。
     同じ ID で設定値が違っていても、現在は無効な設定値でも、既存を返す。
  3. 既存が無いときだけ、要求全体を `startRunRequestSchema` で検証し、`validateChunkSettings` と
     `validateHardTimeouts`（下記）で意味を検証する。違反は 400 `invalid-run-settings`。
  4. `findManuscriptVersion`（404）→ `startRun` → 201。
- 意味検証を `startRun` の前に置く理由：`startRun` は `InvalidChunkSettingsError` を例外にせず
  `stopped` / `settings` の実行を**作る**（PR9b の設計。CLI と同じ経路で記録を残すため）ので、事前に弾かないと
  入力の誤りごとに実行の行が増える。`startRun` 側は二重の防御。
- `validateHardTimeouts`（`checkMs` / `recheckMs` が 1 以上の安全な整数で、`recoveryConfirmMs` を足しても
  `MAX_TIMEOUT_MS` を超えない。PR9b 決定 44）は現在 `orchestrator.ts` の非公開関数。**`run/timeouts.ts` の
  純粋関数として切り出し**、オーケストレーターとハンドラーの両方がそれを呼ぶ（式を複製しない）。
- 同じ `startOperationId` の 2 回目は既存の実行を 200 で返す（PR9b 決定 12。409 にしない。連打した
  クライアントが同じ画面へ進めるようにするため）。
- 空本文（`body.length === 0`）は `POST /api/manuscripts` / `upload` で 400 `empty-body`。仕様 5.1
  「空の本文では検査を開始できない」を、保存できない形で守る（`POST /api/runs` は空本文を見ない）。

### 決定 15：絞り込みはサーバーでしない。一覧と詳細を分ける

指摘は原稿 1 万字で高々数百件なので、絞り込み（分類・採否・再確認状態・位置特定失敗）は PR12 が
クライアント側で行う。`GET /api/runs/:id/findings` にクエリパラメーターは付けない。

一覧の `FindingDto` は理由・再確認要約・採否まで含め（一覧画面の絞り込みに要る）、元候補と位置診断は
`GET /api/findings/:id` の `FindingDetailDto` にだけ入れる（詳細パネルでしか使わず、診断は大きい）。
`listFindings` の N+1（PR9b 持ち越し）はここでは直さない（PR12 で件数を見て判断）。

### 決定 16：エクスポートは PR13

ロードマップは PR10 に `GET /api/runs/:id/export` を置いていたが、形式は評価ツール（PR13）と揃えて
決めるほうが二度手間にならない。仕様 8.2 の「保存済み結果の再閲覧」は `GET /api/runs/:id` と
`findings` で満たす。ロードマップの PR10 節・PR13 節を更新する。

### 決定 17：接続断で `failed` になった単位の復旧は 2 段のまま

PR9b 持ち越しのとおり、生成中に応答を受け取れないまま接続が切れた単位は `failed` のまま残り、
復旧には「再開」→「失敗単位の再試行」の 2 段が要る。1 段にするには `UnitFailure` の拡張と
PR9 決定 20 の改訂が要り、HTTP 層と無関係な変更が同じ PR に混ざるので本 PR では広げない。
`GET /api/runs/:id` の `progress.checkUnits.failed` で失敗件数が取れるので、PR12 は
「再開したあと失敗単位を再試行してください」と案内できる。決定 20 の改訂は持ち越しのまま残す。

### 決定 18：graceful shutdown は走っている実行を待たない

`index.ts` で `SIGINT` / `SIGTERM` を受けたら、①`server.close(cb)`（新規受付停止。**await しない**。Node の
`close` は全接続の終了を待つが、SSE は自然には終わらない）→ ②`hub.closeAll()`（全 SSE を閉じる）→
③`server.closeAllConnections()`（残った keep-alive 接続を切る）→ ④`cb` を待つ → ⑤`connection.current().client.close()`
（undici `Agent.close()`。進行中の要求は流す）→ ⑥`close()`（DB）→ `process.exit(0)`。全体に 5 秒の上限を置き、
超えたら `process.exit(1)`。走っている実行は**待たない**。LM Studio 側の生成は止められない前提なので、次回起動の
`reconcileOnStartup` が `backend-restarted` として照合する（PR9 決定 13）。2 回目のシグナルは即終了。

Windows は `SIGTERM` が届かず、コンソールの Ctrl+C（`SIGINT`）だけが対象。その旨を README に書く。

### 決定 19：`LmStudioClient.close()` を足す

PR7 からの持ち越し。undici の `Agent` を `close()` する。`ConnectionManager.update` が古いクライアントを
閉じるときと shutdown で使う。テストのフェイククライアントは no-op でよい。

### 決定 20：ファイル入力は multipart、`ingestUtf8Bytes` だけを通す

`POST /api/manuscripts/upload` は `c.req.parseBody()` で `file`（`File`）と `name`（文字列）を受け取り、
`new Uint8Array(await file.arrayBuffer())` を `ingestUtf8Bytes` に渡す。`Utf8DecodeError` は 400
`invalid-utf8`。CRLF は保持される（バイト列で受けるため。仕様 5.1）。`name` が無ければ `file.name` を使い、
その結果に `createManuscriptRequestSchema` の `name`（1〜200 文字）と同じ制約を適用する。`file` が `File` で
ない、`name` が文字列でない、同名項目が複数ある（`parseBody` が配列を返す）場合は 400 `validation`。Hono にも `@hono/node-server` にも本文サイズの上限は無く、本 PR でも設けない
（仕様 9「上限は実測後に決める」）。

## タスク分解

> **エージェント向け**：superpowers:subagent-driven-development で 1 タスクずつ実装する。各タスクは
> 「失敗するテストを書く → 落ちるのを見る → 最小の実装 → 通す → コミット」を単位とし、完了時に `pnpm check`
> を通す。本書の「エンドポイント」「DTO」「要求」「SSE」節と決定 1〜20 が要件の正本で、タスクはその割り付けである。
> 相対 import は `.ts` 拡張子付き。識別子は英語、コメント・コミットメッセージは日本語。

```
Task 1（shared の型と語彙）→ Task 2（接続の管理）→ Task 3（オーケストレーター）→ Task 4（API の土台）

  → Task 10（shutdown・漏えい検査・ドキュメント）
```

### Task 9：SSE（決定 12・13）

**Files**
- Create: `packages/server/src/api/events.ts`（`toRunEventDto(event: RunEvent): RunEventDto` と route）
- Modify: `packages/server/src/api/router.ts`
- Test: `api/events.test.ts`（A6）

**手順**
1. **最初に前提を確かめる**：`app.request("/api/runs/x/events", { signal })` を abort したとき `stream.onAbort` が
   呼ばれるかを最小の route で確認する。呼ばれなければ、A6 は `@hono/node-server` の `serve` を任意ポートで
   起動して実 HTTP で書く（`client.test.ts` C47 と同じ道具立て）。結果をテストファイル冒頭のコメントに残す。
2. `toRunEventDto`：本書「SSE」節の写像（`recheck-finished` の `disabled` / `suppressed` → `not-applicable` +
   `notApplicableReason`）。`run-finished` は到達しない（`PipelineEvent` の型に合わせて `never` で弾く）。
3. route：`findRun` → 404 → `streamSSE(c, async (stream) => { ... })`。中身は決定 12 の機構そのまま：
   ```ts
   let chain = Promise.resolve();
   let done!: () => void; const closed = new Promise<void>((r) => { done = r; });
   const finish = () => { unsubscribe(); clearInterval(ping); done(); };
   const send = (dto: RunEventDto) => { chain = chain.then(() => stream.writeSSE({ event: dto.type, data: JSON.stringify(dto) })).catch(finish); };
   const unsubscribe = hub.subscribe(runId, {
     onEvent: (e) => { const dto = toRunEventDto(e); send(dto); if (dto.type === "run-settled") chain.then(finish, finish); },
     onClose: finish,
   });
   const current = findRun(db, runId);      // 購読の後に読む（決定 12 の順序）
   if (current !== null && current.status !== "running") { send({ type: "run-settled", status: current.status, stopReason: current.stopReason }); chain.then(finish, finish); }
   const ping = setInterval(() => { chain = chain.then(() => stream.write(": ping\n\n")).catch(finish); }, deps.ssePingIntervalMs ?? 15_000);
   stream.onAbort(finish);
   await closed;
   ```
4. A6 を本書のとおり。`writeSSE` の reject は、応答の `body` を先に `cancel()` してから `emit` して再現する。
5. `pnpm check`。

**完了条件**：A6 が緑。abort 後もフェイクの `chat` 回数が増える。
