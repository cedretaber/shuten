# PR11 詳細計画：接続・入力・設定画面（web）

作成日：2026-09-10
状態：設計済み（タスク分解は未）
仕様：`docs/spec/mvp-spec.md`（v0.9）4（手順 1〜4）、5.1、5.2、7（モデル種別による絞り込み）、
8.2（二重送信、再開と新規の区別）、9（ループバック）、11 節（1・2 項の UI 側）
前提：`docs/plans/2026-09-07-mvp-roadmap.md` の PR11 節、`docs/reference/invariants.md`、
`docs/plans/2026-09-09-pr10-http-api.md`（決定 1〜19。API の契約はここが正本）

## 目標

PR10 で用意した HTTP API を、ブラウザから使える画面にする。すなわち、

- アプリの骨格（ルーティング、共通レイアウト、ヘッダーの接続状態）
- API クライアント（`fetch` の薄い包み。型と zod スキーマは `packages/shared/src/api/` から取る）
- `features/connection/`（接続先・API キー・接続確認・モデル選択）
- `features/manuscript/`（貼り付けとファイル読み込み、原稿版の確定）
- `features/settings/`（検査設定と検査の開始）
- `features/run-receipt/`（開始した実行の受付表示）
- コンポーネントの単体テスト基盤（Vitest ＋ Testing Library。導入はこの PR）

本 PR の終点は「検査を開始でき、実行 ID と状態が表示される」ところまでである。
結果の閲覧は PR12a、進捗・実行制御・SSE は PR12b が作る。

## Windows での確認（着手の前提ではなく、マージ条件）

ロードマップのチェックポイント「Windows でのローカル確認」は、当初 PR11 の**前**に置いていたが、
2026-09-10 に **PR11 の実装後・マージ前**へ移した。理由は 2 つある。

- CI の `check` ジョブは `matrix: [ubuntu-latest, windows-latest]` で回っており、Windows 側で
  依存の導入・型検査・lint・テスト・`pnpm build`・better-sqlite3 のバインディング読み込みまで通っている。
  ガイドの旧手順 1・2・3・5 は CI が毎回確認している内容と同じである。
- CI が確認していないのは `pnpm start` から先（静的配信、SPA の直リンク、ブラウザ操作、LM Studio 接続、
  コンソールからの終了）だけで、**それはまさに本 PR が作る画面である**。PR11 より前に確認しても、
  確認対象が本 PR で置き換わる。

したがって手順は次の順で行う。

1. PR11 を実装する
2. CI を Ubuntu・Windows とも緑にする
3. PR11 のブランチをネイティブ Windows で起動確認する（`docs/guides/windows-verification.md` の 2 節）
4. 問題があれば同じ PR で直す
5. マージする

3 に **Ctrl+C による終了の確認を含める**。`packages/server/src/index.ts` の graceful shutdown は
「Windows には `SIGTERM` が届かず、コンソールの Ctrl+C（`SIGINT`）だけが対象」という前提で書いてあるが、
その経路は CI を通らず、PR10 の時点でも実機確認をしていない。`shutdown: done` まで進んでプロセスが
終了し、もう一度 `pnpm start` できること（SQLite のハンドルが閉じていること）まで見る。

結果は `docs/decisions/0002-scaffold-conventions.md` の「検証状況」に記録する。合成原稿の本文や
機器固有の値（IP アドレス、ユーザー名を含むパス）は記録に含めない。

- 依存の版は完全固定。相対 import は `.ts` 拡張子付き。scripts は Windows で動く書き方。
- 公開リポジトリ。個人情報・機器固有の値・実原稿をコミットしない。

## 決定

### 決定 1：本 PR の終点は「実行の受付表示」まで

検査の開始（`POST /api/runs`）が実際に通るところまでを本 PR に含める。仕様 4 節の手順 4 が
「検査を開始する」であり、ロードマップが「11 節 1 項は最初の検査実行で満たす」としているため。

開始した直後に利用者が見るのは、次だけとする。

- 再表示可能な URL（`/runs/:id`）へ遷移する。
- 表示するのは実行 ID と現在の `status`（および `stopReason` / `stopMessage`）。
- 初回は `POST /api/runs` の応答（作成直後のスナップショット）、再読み込み時は
  `GET /api/runs/:id` を **1 回だけ**取得する。手動の「最新の状態を取得」だけ用意する。
- 進捗、結果、停止・再開・再試行、SSE、ポーリングは**含めない**。

存在しない実行 ID、取得失敗、開始失敗の表示を用意する（決定 16）。

### 決定 2：画面割りは「主動線 1 ページ ＋ 接続は別画面」

| パス | 画面 | 中身 |
| --- | --- | --- |
| `/` | 原稿と検査設定 | 原稿の確定 → 検査設定 → 開始 |
| `/settings/connection` | 接続設定 | 接続先 URL、API キー、接続確認、モデル選択 |
| `/runs/:id` | 受付表示 | 実行 ID と状態（決定 1） |
| `*` | 画面内 404 | 「そのページはありません」と `/` へのリンク |

接続設定はサーバーの `settings` 表に残るため、実際に触るのは初回と接続先を変えるときだけである。
毎回の動線から外し、ヘッダーに状態を常時表示する。ヘッダーは PR12a で結果画面が増えても使える。

### 決定 3：ルーティングは `react-router` の宣言的 API だけを使う

使うのは `BrowserRouter` / `Routes` / `Route` / `Link` / `useParams` / `useNavigate` / `useLocation`、
テストでは `MemoryRouter`。`loader` / `action` / `createBrowserRouter` は使わない。通信は API
クライアントに置き、ルーターにデータ取得の責務を持たせない（PR12 で責務が混ざるのを防ぐ）。

自前の薄いルーターを書く案は退けた。100 行程度で書けても、`popstate`、`pushState` 後の再描画、
修飾キー付きクリック（Ctrl/Cmd ＋クリックで別タブ）、パスパラメーターの解析、直接アクセス、
テスト用の履歴を自分で正しく扱う必要がある。PR12a で実行一覧、PR12b で状態復元が加わり、
ルーティングは一時的な補助ではなくアプリの骨格になる。保守対象を増やす費用のほうが大きい。

`react-router@8.3.1` は `BrowserRouter` などを本体エントリから公開しており、`react-router-dom` は
要らない。peer は `react >=19.2.7`（当リポジトリは 19.2.8）、直接依存は `cookie-es` だけである。

サーバー側の SPA フォールバックは PR10 で入っている（`packages/server/src/app.ts`。`/api` 以外は
`index.html` を返す）。vite の dev server も既定でフォールバックする。History API 方式に
server 側の変更は要らない。

### 決定 4：足す依存はこれだけ

```
dependencies:
  react-router                    8.3.1
devDependencies:
  @testing-library/dom            10.4.1   （@testing-library/react の peer）
  @testing-library/jest-dom       7.0.1
  @testing-library/react          16.3.3
  @testing-library/user-event     14.6.7
  jsdom                           30.0.1
```

`@testing-library/dom` は `@testing-library/react@16.3.3` が peer として要求する。pnpm は peer を
自動で補わないので直接 devDependency に置く。

足さないもの：CSS フレームワーク、UI コンポーネントライブラリ、TanStack Query などのサーバー状態
管理、MSW。PR11 の通信は接続確認・原稿作成・原稿取得・開始・実行 1 件の取得だけで、キャッシュも
自動再検証も要らない。SSE と進捗が入る PR12b で改めて検討する。API のモックは `fetch` の注入で行う
（決定 14）。

### 決定 5：CSS は素の CSS ＋ CSS Modules

- 色・余白・文字サイズを CSS カスタムプロパティで `styles/tokens.css` に定義する。
- リセットと共通レイアウトを `styles/global.css` に置く。
- feature 固有のスタイルは CSS Modules（vite 標準。依存ゼロ）。
- ボタン・入力・エラー表示の共通コンポーネント化は、反復が確認できてから行う。

PR12a の本文表示・指摘一覧・強調表示・左右ペインは独自性が高く、既成のフレームワークを入れても
中心部分は個別実装になる。設定・更新・命名規則・アクセシビリティ確認の対象を増やす費用に見合わない。

### 決定 6：ブラウザ側の永続化は `localStorage`

| キー | 値 | 既定 |
| --- | --- | --- |
| `shuten.v1.selectedModelId` | モデル ID の文字列 | 未選択 |
| `shuten.v1.runSettings` | 検査設定一式（許容語を除く） | `RUN_SETTINGS_DEFAULTS` |
| `shuten.v1.allowedWords` | `{ manuscriptVersionId, allowedWordsRaw }`（決定 7） | なし |
| `shuten.v1.manuscriptVersionId` | 直近に確定した原稿版 ID | なし |

**置かないもの**：API キー（サーバーのプロセスメモリだけ、という PR10 決定 5 を崩さない）、
接続先 URL（サーバーの `settings` 表が正本）、本文（正本はサーバーの原稿版。10 万字級では容量的にも
入らない）。

読み出しは必ず zod で検証し、壊れていたらそのキーを消して既定値に戻す。`localStorage` が使えない
環境（プライベートウィンドウなど）で例外が出ても画面が落ちないよう、読み書きを try/catch で包む。

保存する検査設定は `StartRunRequest` とは**別の形**である（`startOperationId`・`manuscriptVersionId`・
`modelId`・`allowedWordsRaw` を含まない）。そのため `storage/local.ts` に専用の
`storedRunSettingsSchema` を定義する。`startRunRequestSchema` を流用しない。

起動時に `shuten.v1.selectedModelId` を接続確認へ渡し、存在しない／生成に使えないなら選択を落とす。
`shuten.v1.manuscriptVersionId` は `GET /api/manuscripts/:id` で確かめ、**404 ならキーを消して
編集中に戻す**。通信失敗・5xx では**消さず**、再試行可能なエラーとして扱う。

### 決定 7：許容語は原稿版と組にして保存する

許容語は作品固有の固有名詞・造語であることが多い。別の原稿へ自動的に持ち越すと、本来出すべき指摘を
黙って抑制することになる。仕様 6.4 の「語の登録だけで周囲の文法や文脈上の誤用まで免除しない」の
趣旨にも反する。

`{ manuscriptVersionId, allowedWordsRaw }` の組で保存し、**同じ原稿版を再表示したときだけ復元する**。
別の原稿を確定したら空から始める。分割長・観点・再確認の有無・生成設定は作品に依存しないので、
従来どおり `shuten.v1.runSettings` に共通で持つ。

### 決定 8：接続確認を投げる契機は 3 つだけ

1. アプリの起動時に 1 回（保存されたモデル ID を添える）
2. 接続設定を保存した直後
3. **検査を開始する直前**

**定期的なポーリングはしない。** 3 が要るのは、`POST /api/runs` の 201 が「作成直後のスナップショット
で、モデル未ロードなどの結末は含まない」ためである（PR10 決定 14）。PR11 には進捗表示が無いので、
未ロードのまま開始すると利用者には `running` に見えたまま黙って失敗する。

ヘッダーの表示は「**最後に確認した時点の状態**」であることが分かる表現にする（確認時刻を添え、
手動の「再確認」を置く）。ポーリングしない以上、LM Studio 側のロード状態は表示後に変わりうる。

`POST /api/settings/connection/check` は試験生成を送らないので（PR10 決定 8）、副作用は無い。

### 決定 9：開始できるモデルの条件は `isGenerationCapable`

開始してよいのは、次がすべて成り立つときだけである。

```
check.reachable === true
  && check.model?.found === true
  && isGenerationCapable(check.models.find((m) => m.id === selectedModelId))
```

`loaded` だけを見てはならない。`loaded` はロード状態しか表さず、embeddings モデルでもロード済みなら
`true` になる。サーバーの生成経路（`packages/server/src/run/executor.ts`）は
`state === "loaded" && (type === "llm" || type === "vlm")` を要求する（仕様 7 節）。ここを揃えないと、
画面上は開始できたのに実行が黙って止まる。

**`ConnectionCheckDto.model` は `{ id, found, state, loaded }` だけで `type` を持たない。**
`type` があるのは `check.models[]`（`ModelInfoDto`）のほうである。判定は `check.models` から
当該モデルを引いて行う。

判定規則を web に書き写さず、`isGenerationCapable` を
`packages/server/src/lmstudio/models.ts` から `packages/shared/src/run/model-capability.ts` へ移し、
server 側は薄い委譲に変える。shared 側は `{ state: string | null; type: string | null }` を受ける
構造的な引数にする。server の `ModelInfo`（`lmstudio/types.ts`）も shared の `ModelInfoDto`
（zod の `z.string().nullable()`）も `type` / `state` が `string | null` なので、どちらもそのまま渡せる。
PR10 で `RUN_STOP_REASONS` などの列挙を shared に移したのと同じ扱いである。二重に持つと片方だけ
直す事故が起きる。

判定に使う `LOADED_STATE`（`"loaded"`）は現在 `packages/server/src/lmstudio/types.ts` にあり、
`client.ts` と `api/settings.ts` も参照している。これも同じファイルへ移し、
`lmstudio/types.ts` からは shared のものを**再エクスポート**して既存の import を壊さない。

モデル一覧の選択肢には `llm` / `vlm` だけを出す。未ロードのものも選択状態は維持し、
「LM Studio でロードしてください」と表示したうえで開始はさせない。種別が `null` や `embeddings` の
ものは選択肢に出さない。

### 決定 10：接続確認の競合は世代番号と `AbortController` で防ぐ

起動時・保存直後・開始直前の確認は重なりうる。古い要求が後から完了して新しい状態を上書きしないよう、
`app/connection-context.tsx` に世代番号を持ち、**最新の要求の応答だけを反映する**。あわせて新しい
要求を出すときは前の要求を `AbortController` で中断し、アンマウント時も中断する。

`signal.aborted` による中断は、画面上の通信エラーとして**表示しない**。

開始処理は context の `checkConnection()` を呼び、**その戻り値を直接判定に使う**。context の更新後の
React state を読み直す形にしない（再描画の順序に依存する）。API クライアントを直接呼ぶのも不可で、
世代番号・`AbortController`・ヘッダーの最終確認時刻の更新を迂回してしまう。

```ts
const result = await connection.checkConnection(modelId);
if (!canStartWithModel(result, modelId)) return;
await api.startRun(snapshot);
```

### 決定 11：原稿版は明示の確定操作で作る

画面の状態は 3 段階とする。

1. **編集中** — 貼り付けた本文、または選択した `File` を保持する。**サーバーには送らない。**
2. **原稿確定済み** — `POST /api/manuscripts`（貼り付け）または `POST /api/manuscripts/upload`
   （ファイル）を実行し、返された原稿版 ID を保持する。サーバーが保存した本文（＝正本）を
   読み取り専用で表示する。
3. **検査受付済み** — 確定済みの原稿版 ID で `POST /api/runs`。開始に失敗しても原稿版 ID を保持し、
   原稿を作り直さず**開始だけを再試行する**。

利点は「孤立した原稿版を発生させない」ことではない。確定後に「別の原稿を選ぶ」を押したり、検査せず
画面を閉じたりすれば、実行から参照されない原稿版は残る。正確には
**「原稿版の作成を利用者の明示的な確定操作にし、検査開始に失敗しても同じ原稿版を再利用する。
開始の再試行によって原稿版が増えることを防ぐ」**である。MVP では削除・原稿版一覧・自動掃除を
追加せず、この未使用レコードを許容する（ローカル利用で数も限られ、清掃機能はライフサイクル設計を
大きくする）。

ファイル入力では、選択した `File` を確定操作まで保持し、**`File.text()` も textarea の値も保存要求に
使わない**。確定時に元の `File` をそのまま multipart で送る。仕様 5.1 の「編集欄の改行変換を保存本文へ
逆流させない」を守るにはこれしかない。CRLF と不正 UTF-8 の判定はサーバーへ一元化される
（不正なら 400 `invalid-utf8`）。

ボタン名は役割で分ける。

- 第 1 段階：「この原稿を確定する」
- 第 2 段階：「検査を開始する」
- 確定後：「別の原稿を選ぶ」（**現在の選択を解除するだけ**。新しい本文を再度確定した時点で次の
  原稿版を作る）

確定後の表示には原稿名・書記素数・確定日時を出し、「**確定後の本文は変更できない**」と明示する。

「この原稿を確定する」の無効化条件は次の 3 つ。

- 貼り付けで本文が空（`length === 0`。**`trim()` はしない** — 空白だけの本文も無加工で保存する対象）
- ファイル未選択
- 原稿名が空、または 201 文字以上

検査設定は**原稿を確定するまで操作できない**。

### 決定 12：検査設定は仕様 5.2 の 6 項目を既定表示、残りは折りたたむ

既定で見せるのは仕様 5.2 の表の 6 つ（検査観点、分割長、初回の参考文脈、再確認の有無、
再確認の参考文脈、許容語）。残り（`maxTokens`、`temperature`、`seed`、`reasoningEffort`、
`roundingTolerance`、`maxInputGraphemes`、`checkMs`、`recheckMs`）は折りたたみの
「詳細な生成設定」に入れる。**変えられるが、既定では見せない。**

初期値は `RUN_SETTINGS_DEFAULTS`。思考は既定で `none`。`seed` は空欄なら送らない。既定値から
変えた項目があれば、閉じたままでもそれと分かるようにする。

根拠は仕様 5.2 末尾の「温度などの最適値や推論モードは現時点で固定しない」と、13 節が
「モデルごとのプロンプト、生成パラメーター、タイムアウト」「分割長と参考文脈長の実測による調整」を
未決にしていること。PR13b の評価で実際に動かす値なので、画面から触れないと毎回 CLI か curl に戻る。

### 決定 13：入力検証の分担

**クライアントで弾く**（shared が持っている規則だけ）：

- 組み立てた `StartRunRequest` 全体を `startRunRequestSchema.safeParse` に通す。整数性、
  各タイムアウトの `1..MAX_TIMEOUT_MS`、観点 1 つ以上、原稿名の長さがまとめて確認できる。
- `validateChunkSettings`（分割設定の整合）。
- 観点は最低 1 つ（最後のチェックを外せなくする）。
- 原稿名 1〜200 文字、本文が空でない。

**サーバーに委ねる**：

- `checkMs + recoveryConfirmMs` の合計上限（`validateHardTimeouts` は `recoveryConfirmMs` を要り、
  これはサーバー設定である）。
- 本文から判明する入力上限超過（決定 16 で受付画面が扱う）。

サーバーから返ったエラーは項目ごとではなく**フォーム全体のエラー**として、開始ボタンの上に 1 か所に
出す。

### 決定 14：API クライアントは `fetch` を注入できる薄い包み

`api/client.ts` に `createApiClient({ fetch })` を置く。既定は `globalThis.fetch`。注入できるように
するのはテストで fake を渡すためで、これが MSW を入れない理由でもある（server 側のテストが fake を
渡す流儀と揃う）。

**PR11 が呼ぶ口だけを作る。**

| 関数 | 呼ぶ口 |
| --- | --- |
| `getConnection()` | `GET /api/settings/connection` |
| `putConnection(body)` | `PUT /api/settings/connection` |
| `checkConnection(modelId?, { signal })` | `POST /api/settings/connection/check` |
| `createManuscript({ name, body })` | `POST /api/manuscripts` |
| `uploadManuscript({ file, name })` | `POST /api/manuscripts/upload` |
| `getManuscript(id, { signal })` | `GET /api/manuscripts/:id` |
| `startRun(body)` | `POST /api/runs` |
| `getRun(id, { signal })` | `GET /api/runs/:id` |

`GET /api/runs`（一覧）、停止・再開・再試行、指摘、採否、復旧確認、SSE は PR12 の担当なので
**書かない**。

応答はすべて `@shuten/shared` の zod スキーマで `parse` する。サーバー側も `respond` で出力を検証して
いるので二重だが、型注釈と実際の JSON がずれたときに実行時に気づける。スキーマは `.strict()` なので、
**余分なキーを含む応答は拒否される**（落とされるのではない）。

例外は 3 種類。

| 例外 | いつ |
| --- | --- |
| `ApiRequestError { status, code, message }` | 非 2xx。本文を `apiErrorSchema` で parse して得る |
| `ApiResponseError` | 2xx だが本文が JSON でない、またはスキーマに合わない |
| `ApiTransportError` | `fetch` 自体が throw した、または**本文の読み取り中に切れた** |

非 2xx の本文が `apiErrorSchema` に合わないとき（HTML が返ってきた等）は、状態コードだけを持つ
`ApiRequestError` に落とし、`code` は `"unknown"` にする。

`response.json()` のストリーム読み取り失敗は `ApiResponseError` ではなく `ApiTransportError` に
分類する（「サーバーが何をしたか分からない」側の失敗であるため）。

multipart は `FormData` に `file`（**選択した `File` をそのまま**）と `name` を入れ、`Content-Type` は
**指定しない**（ブラウザに boundary を付けさせる。自分で書くと壊れる）。

クライアント独自のタイムアウトは**設けない**。PR11 が呼ぶのは同期処理だけで（`POST /api/runs` は
分割計画までで、生成は投げない）、独自の打ち切りは「結果不明」の状態を自分で増やすことになる。

### 決定 15：開始結果が不明かどうかは例外クラスと別の述語で判定する

`startOperationId` の使い回しは、例外の種類ではなく `isStartOutcomeUnknown()` という別の述語で決める。

| 結果 | 条件 | `startOperationId` |
| --- | --- | --- |
| **確定** | 有効な `RunDto` を受け取った | 使い切り。押し直しは新しい ID |
| **確定** | 4xx で本文まで読めた（契約どおりのエラー応答。作成前の拒否） | 使い切り。押し直しは新しい ID |
| **不明** | `fetch` が throw した | 保持して再試行 |
| **不明** | 本文の読み取り中に切れた | 保持して再試行 |
| **不明** | 2xx だが契約違反（JSON でない、スキーマに合わない） | 保持して再試行 |
| **不明** | 5xx | 保持して再試行 |

5xx を「不明」に入れるのが要点である。サーバーが実行を作った後の処理で落ちた可能性があるため、
確定扱いにすると二重に作る。

`POST /api/runs` は**二重送信を 409 にしない**。同じ `startOperationId` の既存実行を見つけたら、
残りの入力を検証も比較もせずに **200** でその実行を返す（PR9b 決定 12、PR10 決定 14。
`api/runs.ts` の手順 2）。新規作成は 201 である。したがって同じ ID での再送は安全で、画面は
**200 でも 201 でも同じように `RunDto` を受け取って `/runs/:id` へ遷移する**。再試行のテストは
「200 を受け取って既存の実行へ遷移する」ことを見る（201 を期待しない）。

作成前の拒否は 400（`validation` / `invalid-run-settings`）と 404（原稿版なし）で、開始経路に
409 は無い（409 を返すのは `PUT /api/settings/connection` の `runs-active` と、停止・再開・再試行の
経路であり、いずれも本 PR の開始処理とは関係しない）。

**再送は ID だけでなく要求内容も固定する。** 送信開始時に `StartRunRequest` 一式をメモリに
スナップショットとして保持し、「不明」からの再試行はそれをそのまま送る。ID だけ固定してフォームの
現在値を送ると、サーバーは既存実行を返すのに画面は新しい設定を映していて、食い違ったまま気づけない。

送信中はボタンを `disabled` にする（連打の防止）。

### 決定 16：受付画面は常に中立表示、状態は網羅 switch で日本語に写す

`GET /api/runs/:id` の `RunDetailDto` を 1 回だけ取る。**ポーリングも SSE もしない。**
手動の「最新の状態を取得」だけ用意する。

画面が読むのは **`RunDto` だけ**である。`POST /api/runs` は `RunDto` を直接返し、
`GET /api/runs/:id` は `{ run: RunDto, progress, targets }` を返すので、どちらの経路でも
`RunDto` を同じ描画関数に渡せる。`progress` と `targets` は**使わない**（進捗の表示は PR12b）。

見出しは**常に中立の「検査実行」**とし、開始直後かどうかで文言を変えない。`location.state` は
履歴の扱いによって再読み込み後も残りうるので、「開始直後だけ」の判定に使わない。

`RunStatus`（5 種）と `RunStopReason`（8 種）は、**`default` の無い網羅 `switch`** で日本語に写す。
値が増えたら型検査で落ちる。

| `RunStatus` | 表示 |
| --- | --- |
| `running` | 実行中 |
| `stopped` | 停止中 |
| `recovery-waiting` | 復旧待ち |
| `completed` | 完了 |
| `partially-failed` | 一部失敗 |

`RunStopReason` は `model-not-loaded` / `recovery-needed` / `connection-lost` / `settings` /
`aborted` / `internal-error` / `recovery-blocked` / `backend-restarted` の 8 つすべてを写す。

`stopMessage` はそのまま表示する。PR10 の制約により接続先 URL を含まないことが保証されている
（`orchestrator.start.test.ts` の O16 が検証している）。

**`stopped` かつ `stopReason === "settings"` は受付成功として見せない。** 「検査は開始できませんでした」
に切り替え、`stopMessage`（入力上限の説明）と「検査設定に戻る」を出す。`POST /api/runs` は 201 を
返すが、その中身がすでに `status: "stopped"` / `stopReason: "settings"` / `stopMessage` 非 null に
なっている場合があるためである（分割時の `InputTooLongError`。`orchestrator.start.test.ts` の
O16・I-1）。仕様 5.2 の「入力上限を超えた場合は黙って縮めず、エラーとして設定変更を案内する」は
ここで満たす。再読み込み後の `GET` でも同じ判定なので表示は変わらない。

404 は「その実行はありません」と `/` へのリンク。

### 決定 17：本文のプレビューは書記素境界で切り、全文は開いたときだけ描画する

確定済みの原稿は、既定で**先頭 500 書記素**のプレビューを出す。`body.slice(0, 500)` は使わない
（サロゲートペア、結合文字、ZWJ 絵文字、CRLF の途中で切れる）。`buildGraphemeIndex(body)` と
`offsetAt(index, 500)` で UTF-16 位置を求めて切る。両方 `@shuten/shared` から公開されている。

全文は折りたたみの中に置くが、**開閉状態を React で持ち、開いているときだけ全文を DOM に足す**。
閉じた `<details>` の子要素も DOM には存在するので、`<details>` に入れるだけでは 10 万字級の描画を
避けられない。全文は `white-space: pre-wrap` で表示する。

書記素数は確定後に `countGraphemes(body)` で **1 回だけ**数える（入力中に毎打鍵で数えない）。

### 決定 18：API キーの扱い

- API キーは `input[type="password"]` の書き込み専用欄で受け取る。**その入力値以外のテキストとして
  描画しない。**
- エラー表示、接続済み表示、ヘッダーに含めない。
- `PUT /api/settings/connection` の要求本文以外の要求へ送らない。
- 例外オブジェクトへ要求本文や API キーを格納しない。
- 保存成功後に入力欄を空へ戻し、`hasApiKey` の表示だけを更新する。
- `localStorage` へ保存しない。
- API クライアントは `console.*` を一切呼ばない。

`PUT` の `apiKey` は三状態である。**空のまま保存＝維持**（要求から省略）、**「消去」＝ `null` を送る**、
**入力あり＝設定**。

`PUT /api/settings/connection` は実行中だと **409 `runs-active`** を返す（PR10 決定 7。
`activeRunIds()` を見ている）。このとき**入力中の URL・API キー欄を消さず**、
「検査実行が走っているため変更できません」をそのまま出す。

接続先 URL は `GET`/`PUT /api/settings/connection` の応答としてしか画面に出さない。実行・原稿・
エラーの表示に出さない。

### 決定 19：テスト基盤

`packages/web/vite.config.ts` の `test.environment` を `node` → `jsdom` に変え、`test.setupFiles` に
`vitest.setup.ts` を指定する。setup では `@testing-library/jest-dom/vitest` を import し、
**`afterEach(cleanup)` を明示的に書く**。このリポジトリは `globals: true` を使わないため
（テストは `vitest` から明示 import する）、Testing Library の自動 cleanup は登録されない。書かないと
テスト間で DOM が残り、原因の分かりにくい失敗になる。

画面のテストは `MemoryRouter` で包み、API クライアントには fake の `fetch` を渡す。
**実際の `fetch` は一度も呼ばない。**

### 決定 20：完了条件に `pnpm build` を含める

`pnpm check` は typecheck・lint・test だけで、vite の本番ビルドを含まない。react-router、
CSS Modules、静的配信を初めて本格的に組む PR なので、`pnpm check` と `pnpm build` の**両方**を
完了条件にする。CI（`.github/workflows/`）は既に `pnpm build` を実行しているが、ローカルで完了を
宣言する前にも通す。

Windows のローカル確認では、さらに `pnpm start` とブラウザからの直接アクセス（`/`、
`/settings/connection`、`/runs/:id` の直リンク）を確認する。

## 画面ごとの仕様

### `/` — 原稿（編集中）

入力方法は「貼り付け／ファイルを読み込む」のラジオで切り替える。原稿名は 1〜200 文字で、
ファイル選択時はファイル名を初期値に入れて編集可能にする。貼り付けは textarea、ファイルは
`input[type="file"]` と選んだファイル名・サイズの表示だけで、**中身は読まない**。

### `/` — 原稿（確定済み）

`POST` の応答をそのまま使い、原稿名・書記素数・確定日時・「確定後の本文は変更できない」を表示し、
先頭 500 書記素のプレビューと、開いたときだけ全文を描く折りたたみを置く（決定 17）。
「別の原稿を選ぶ」で編集中に戻る。

### `/` — 検査設定と開始

決定 12 の構成。「検査を開始する」を押したときの順序は次のとおり。

1. `connection.checkConnection(modelId)` を呼び、**戻り値**で決定 9 の条件を判定する
2. 通らなければ `POST /api/runs` を**投げず**、接続設定へのリンク付きでエラーを出す
3. 通れば `StartRunRequest` を組み立て、`startRunRequestSchema` で検証し、スナップショットに固定して
   `POST /api/runs`
4. `RunDto` を受け取ったら `navigate(runPath(run.id))`

無効化条件は「原稿が未確定」「モデルが未選択」の 2 つ。未選択のときは接続設定へのリンクを出す。

### `/settings/connection`

`GET` で現在の `endpointUrl` と `hasApiKey` を表示する。API キーは決定 18 の三状態。モデル一覧は
`check.models` から `llm` / `vlm` だけを出す（決定 9）。409 `runs-active` の扱いは決定 18。

### `/runs/:id`

決定 16 のとおり。
