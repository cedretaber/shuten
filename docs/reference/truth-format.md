# 正解ファイルの書き方

`pnpm eval evaluate` / `pnpm eval aggregate` が読む「正解ファイル」の形式。
仕様書 10 節の評価で使う、**実在した誤字・脱字と、誤検出してほしくない正常な文章の一覧**を
1 つの JSON ファイルにまとめたもの。

このファイルは利用者（作者）が手で書く。値域を間違えると、正解ファイル自体は正しく読み込めても
「その正解項目は絶対に検出できない」「原稿が変わったのに気付かずに古い正解で採点する」といった
**静かな誤集計**につながる。このドキュメントの表と手順を守って書くこと。

形式の正本は実装（`packages/cli/src/eval/truth.ts` の zod スキーマ）である。
このドキュメントとスキーマが食い違ったら、実装（とエラーメッセージ）を信じること。

**このドキュメントの例はすべて合成（架空）の原稿・正解データである。** 実際に評価に使う原稿・
正解ファイルは、実原稿と同じ扱いでリポジトリの外に置く（後述「ファイルの置き場所」）。

## ファイル全体の形

```json
{
  "formatVersion": "1",
  "manuscript": {
    "name": "評価用サンプル原稿A",
    "bodyHash": "8f8a821cfd5f39e4037fdf0c269a48aa10d7c42e1f001655c07bb4ad7ec58660"
  },
  "entries": [
    { "...": "誤り項目・正常項目（後述）" }
  ]
}
```

- `formatVersion`：正解ファイルの形式の版。今のところ常に `"1"`（文字列）。
- `manuscript.name`：人が見るための原稿名。**原稿のファイルパスは書かない**
  （機器固有の値をファイルに残さないため。名前は自由文字列でよい）。
- `manuscript.bodyHash`：評価対象の原稿本文のハッシュ値。原稿・正解ファイル・結果 JSON の
  3 つが同じ原稿を指していることの照合に使う（後述「`bodyHash` の取り方」）。
- `entries`：正解項目の配列。**誤り項目（`kind: "error"`）と正常項目（`kind: "normal"`）を
  同じ配列に混ぜて入れる。**

### 記入例（合成）

次は、架空の原稿

```
0: ある朝、少年は森へ向かって歩きはじじめた。
1:
2: 「おーい、待ってーな」と少年の後ろで声がした。
```

（段落 ID の数え方は後述。段落 1 は空行そのものである）

に対する正解ファイルの例。

```json
{
  "formatVersion": "1",
  "manuscript": {
    "name": "評価用サンプル原稿A",
    "bodyHash": "8f8a821cfd5f39e4037fdf0c269a48aa10d7c42e1f001655c07bb4ad7ec58660"
  },
  "entries": [
    {
      "id": "e001",
      "kind": "error",
      "perspective": "typo",
      "paragraphId": 0,
      "quote": "はじじめた",
      "occurrence": 1,
      "expected": "はじめた",
      "note": "「じ」が 1 文字多い"
    },
    {
      "id": "e002",
      "kind": "error",
      "perspective": "naturalness",
      "paragraphId": 2,
      "quote": "待ってーな",
      "occurrence": 1,
      "note": "語尾の伸ばし棒が不自然（架空の例）"
    },
    {
      "id": "n001",
      "kind": "normal",
      "paragraphId": 2,
      "quote": "おーい",
      "occurrence": 1,
      "note": "意図した掛け声。誤字・不自然さとして指摘してほしくない"
    }
  ]
}
```

## 2 種類の項目

`entries` の各要素は `kind` で 2 種類に分かれる。**必須項目が種類ごとに違う。**

### `kind: "error"`：拾ってほしい誤り

実在する誤字・脱字、または日本語として不自然な箇所。**`perspective` が必須**で、
`"typo"`（誤字・脱字）か `"naturalness"`（日本語の不自然さ）のいずれかを書く
（仕様書 10 節「誤字・脱字と、日本語の不自然さは別々に集計する」に対応）。

- `expected`（任意）：望ましい修正後の文字列。人が「修正案の妥当性」を見るときの参照に使うだけで、
  **機械は判定に使わない**（書いても書かなくても検出率には影響しない）。

### `kind: "normal"`：指摘してほしくない正常な文章

意図した口語・省略・倒置・造語・反復など、誤りではないのに誤検出されがちな箇所。
**`perspective` は持たない**（指摘側がどの観点で誤検出したかは、指摘そのものの観点で数える。
正常項目の側に観点を持たせても意味がないため）。

## 値域の表

すべて zod スキーマ（`packages/cli/src/eval/truth.ts`）で検証される。表の制約を外れると
正解ファイルの読み込み自体が失敗し、**集計は一切行われない**（部分的な数字を出さない）。

| 項目 | 必須 | 型・制約 | 既定値 | 外したときに起きること |
| --- | --- | --- | --- | --- |
| `formatVersion` | 必須 | リテラル `"1"` | なし | 別形式のファイルを黙って読んでしまう |
| `manuscript.name` | 必須 | 任意の文字列 | なし | （制約なし。原稿のパスは書かないこと） |
| `manuscript.bodyHash` | 必須 | 小文字 16 進 64 文字（`/^[0-9a-f]{64}$/`） | なし | 大文字・切り詰めたハッシュは常に不一致になり、原因が分からないエラーになる |
| `entries[].kind` | 必須 | `"error"` \| `"normal"` | なし | — |
| `entries[].id` | 必須 | 空文字不可。**全項目を通して一意** | なし | 重複するとレポートと正解ファイルを突き合わせられない（読み込み時にエラー） |
| `entries[].perspective` | `kind: "error"` のとき必須（`normal` では持たない） | `"typo"` \| `"naturalness"` | なし | 観点別の検出率が計算できない |
| `entries[].paragraphId` | 必須 | 0 以上の整数 | なし | 負値・小数はエラー。0 起点であることを誤解すると別の段落を指す（後述） |
| `entries[].quote` | 必須 | **空文字不可** | なし | **空文字を許すとゼロ長の範囲になり、どの指摘とも絶対に重ならない「検出されない正解項目」が静かに残る。必ず拒否される** |
| `entries[].occurrence` | 任意 | 1 以上の整数（1 起点） | `1` | 0 起点のつもりで `0` を書くとエラー。省略すれば「その段落内で最初に出てくる一致」になる |
| `entries[].expected` | 任意（`error` のみ持てる） | 任意の文字列 | なし | 機械は読まない（人が見る参考情報） |
| `entries[].note` | 任意 | 任意の文字列 | なし | 機械は読まない（自由記述） |

## 位置の指定方法：`paragraphId` ＋ `quote` ＋ `occurrence`

正解項目が本文のどこを指すかは、近似一致や文字オフセットではなく
**「段落 ID の中で `quote` に完全一致する箇所の、`occurrence` 番目」**で指定する。

> **段落 ID は 0 起点で、空行も 1 段落として数える。**
> エディターの行番号（多くは 1 起点）とも、目で数えた「段落」（空行を除いて数えがち）とも
> **一致しない。** ここを取り違えるのが最も多い間違いなので、必ず数え直すこと。
>
> 上の記入例で言うと：
> - 段落 0：`ある朝、少年は森へ向かって歩きはじじめた。`
> - 段落 1：（空行そのもの）
> - 段落 2：`「おーい、待ってーな」と少年の後ろで声がした。`
>
> 「2 番目に書かれている文」のつもりで `paragraphId: 1` と書くと、実際には空行を指してしまい、
> 解決に失敗する。

- **`quote` は完全一致でのみ照合する**（近似一致・部分一致では確定しない。仕様書 6.3 と同じ規則）。
  引用は原稿の文字列と 1 文字も違わず一致していなければならない。
- **`quote` は 1 つの段落に収まっていなければならない。** 段落をまたぐ誤り（閉じ括弧の欠落など）は
  1 項目で書けない。**2 つの項目に分けて書く**（この場合の作り方に決まった型はないので、
  それぞれの段落に収まる範囲で自然に分割する）。
- **`occurrence`** は、同じ `quote` がその段落内に複数回現れるときに、何番目の出現を指すかを
  1 起点で指定する。省略すると `1`（最初の出現）。
  - `quote` が自己重複する文字列（例：本文「あああ」に対する `quote: "ああ"`）では、
    重なった出現も別々に数える（`ああ` の 1 番目は位置 0〜2、2 番目は位置 1〜3）。
- 書記素クラスタの内側に落ちる一致（サロゲートペア・結合文字・異体字セレクタの途中）は
  一致として採らない（仕様書 6.3 と同じ規則。原稿側がそのような境界を持つ場合のみ関係する）。
- `error` の項目と `normal` の項目が指す範囲が重なっていてはならない（正解として矛盾するため）。

**解決に失敗する条件はすべて 1 回の実行でまとめて報告される**（1 件ずつ直して再実行する必要はない）。
失敗する条件は次のとおり。

- `paragraphId` が原稿の段落数を超えている
- 指定した段落内に `quote` と完全一致する箇所が 0 件
- 一致は見つかるが `occurrence` 件に満たない
- `error` の項目と `normal` の項目の範囲が重なっている

**失敗時に標準エラー・標準出力に出るのは `id`・`paragraphId`・見つかった件数だけ**（決定 9。
原稿の断片や `quote` そのものは出ない）。段落の本文や見つかった一致の位置まで見たいときは、
`evaluate` / `aggregate` に **`--report` を付けて実行する**。指定したときだけ、失敗した段落の
本文と見つかった一致の位置がレポートファイル（Markdown）に書かれる。

## `bodyHash` の取り方

`manuscript.bodyHash` は、評価する原稿本文のハッシュ値（sha256、小文字 16 進 64 文字）。
評価の実行時に、次の 3 つが同じ原稿を指しているかどうかの照合に使われる（1 つでも違えば
集計せずにエラー終了する）。

1. `--manuscript` で読み込んだ原稿本文
2. 正解ファイルの `manuscript.bodyHash`
3. 評価対象の結果 JSON の `conditions.manuscript.bodyHash`（`pnpm eval run` などで作った結果 JSON に
   自動で入る）

値は次のコマンドで得る。

```sh
pnpm eval hash --manuscript <原稿ファイルへのパス>
```

標準出力にハッシュ値が 1 行だけ出る（LM Studio には接続しない）。この値をそのまま
`manuscript.bodyHash` に貼る。

> **`sha256sum <原稿ファイル>` の結果とは一致しない。** `pnpm eval hash` が計算するのは
> ファイルの生バイト列のハッシュではなく、**BOM を除いた後の本文文字列**のハッシュである。
> BOM 付きのファイルでは `sha256sum` の値と必ずずれる。ハッシュ値は必ず `pnpm eval hash` で取ること。

原稿を 1 文字でも直したら、`bodyHash` は必ず変わる。原稿を直した後は
`pnpm eval hash` を取り直して正解ファイルに貼り直す（貼り直さないと、評価が
「原稿と正解ファイルの `bodyHash` が一致しません」で止まる。これは仕様どおりの動作であり、
違う版の原稿に対する正解で気付かずに採点することを防ぐための検査である）。

## ファイルの置き場所

**正解ファイルはリポジトリに入れない。** 実原稿と同じ扱いで、リポジトリの外の場所に置く
（公開リポジトリのため、実在した誤りの一覧や実原稿の引用が漏れないようにする）。

## 使い方

正解ファイルができたら、結果 JSON（`pnpm eval run ...` または `pnpm eval` の既定サブコマンドで
作ったもの）と突き合わせる。

### 1 回の実行を採点する：`evaluate`

```sh
pnpm eval evaluate --manuscript <原稿> --truth <正解.json> --result <結果.json> \
                   [--out <指標.json>] [--report <レポート.md>]
```

- `--out` を省略すると、指標 JSON を標準出力に書く。
- `--report` を指定すると、Markdown のレポート（未検出の一覧、誤検出の一覧、抑制された指摘の一覧、
  人が埋める欄など）を書く。正解の解決に失敗したときは、このレポートに段落本文と一致位置が出る
  （前述「位置の指定方法」）。
- 終了コードは 0（集計できた）／ 1（引数・入出力の誤り、ハッシュ不一致、正解の解決失敗など）。
  **指標の良し悪しでは終了コードを変えない**（合否の判定はしない）。

### 複数回実行のぶれを集計する：`aggregate`

同じ条件で複数回実行した結果のぶれ（非決定性）を見るためのサブコマンド。**`--result` を 2 本以上**
指定する。

```sh
pnpm eval aggregate --manuscript <原稿> --truth <正解.json> \
                    --result <結果1.json> --result <結果2.json> [--result ...] \
                    [--out <集計.json>] [--report <レポート.md>]
```

`--result` に渡した結果 JSON どうしで実行条件（モデル・観点・分割設定・タイムアウトなど）が
1 つでも食い違うとエラーになる（条件が違う実行を混ぜた数字は読めないため）。

### 起動方法について

`pnpm eval <サブコマンド>` はルートの `package.json` に足したショートカットで、実体は次と同じ。

```sh
node packages/cli/bin/shuten-eval.ts <サブコマンド> [オプション...]
```

どちらの書き方でも同じように動く。

## よくある間違い（解決に失敗したときに見る場所）

正解ファイルは正しく読み込めるが、正解の位置解決（`resolveTruthEntries`）に失敗する場合。
まず `--report` を付けて再実行し、レポートに出る段落本文・一致位置を見ながら次を確かめる。

- **段落 ID の起点を間違えている。** `paragraphId` は 0 起点で、空行も 1 段落として数える。
  エディターの行番号や、目で数えた「段落」とはずれる（前述「位置の指定方法」）。
  まず疑うべき間違いはこれ。
- **引用（`quote`）が原稿と 1 文字でも違う。** 全角・半角、送り仮名、句読点の違いも完全一致の対象。
  レポートに出る段落本文をそのまま見て、`quote` を貼り直す。
- **`occurrence` が実際の出現数より大きい、または足りない。** 同じ語句がその段落に何回出てくるかを
  数え直す。レポートには見つかった一致の位置が出るので、件数を確認できる。
- **`error` の項目と `normal` の項目の範囲が重なっている。** 同じ箇所を「誤り」と「正常」の
  両方に登録していないか確認する。正解として矛盾しているため、両方を見直す。
